An agent built from `agent.yaml` needs services before it can run: Postgres, a model gateway, a
trace collector, sometimes project helpers. A project declares them in `stack.yaml` next to
`agent.yaml`, and one command starts them:

```sh
cd src/agentbreeder/examples/northwind
agentbreeder services up --environment dev --env-file ~/.env   # shows the grant; --yes confirms
agentbreeder release agent.yaml --stack . --environment dev    # build, candidate, evals, promote
agentbreeder services down --purge --yes                       # remove everything up made
```

`agent.yaml` doesn't change and still grants nothing. `services up` writes the operator config
for a **local demo environment** outside the repo, under `~/.agentbreeder/stacks/`, and
`--stack DIR` points `build`, `deploy`, `eval`, `release`, `status`, `remove` and `reconcile` at
it.

## stack.yaml

```yaml
kind: stack
schema_version: 1
name: northwind
services:
  postgres:
    ref: service/postgres-pgvector@1.1.0
    with:
      databases: [support, litellm, phoenix]   # one database and one login role each
      init_sql: stack/db/commerce.sql          # schema, seed data and grants
      init_sql_database: support
      roles: [support_agent, support_ops]      # least-privilege roles in `support`
      roles_database: support
  litellm:
    ref: service/litellm@1.0.0
    with: {config: stack/litellm/config.yaml}
    wire: {database-url: postgres.databases.litellm}
  phoenix:
    ref: service/phoenix@1.0.0
    wire: {database-url: postgres.databases.phoenix}
environment:
  gateway: litellm
  models: [support-model, support-embedding, support-judge]
  ceilings: {budget_usd: 50, rpm: 300}
  bindings:
    DATABASE_URL: {ref: postgres.roles.support_agent}   # can't approve its own requests
  eval_database: {ref: postgres.databases.support}
  agents:
    northwind-support: {sponsor: support-lead@example.com, review_by: "2027-06-30", candidate: true}
```

- `with` sets a service's params; `wire` connects its inputs to other services' outputs, so
  services never name each other.
- Secret outputs are only ever used whole: wired to a service, or bound into the agent as a
  mounted file. They never appear in environment variables or labels.
- `stack.lock` records the hash of every service version and file param; `--locked` refuses any
  change, and `up --update` accepts an edited project file (never a changed published version).
- Give the agent the narrowest database role that works. In Northwind the agent can file
  cancellation requests but can't approve one or change an order; only the ops role can.

## What `services up` does

1. Locks the service versions and checks params, wiring and the gateway's model aliases.
2. Prints the **grant**: every service and its image (built-in or project), egress, which
   networks can reach it, its `127.0.0.1` ports, imported variable names, what agents receive, the
   gateway's models and where each provider key goes. It needs `--yes` the first time and
   whenever the grant changes.
3. Generates and imports secrets, builds project services, starts everything, waits for health,
   and runs one-shot `init` and `bootstrap` steps (creating database roles, minting Phoenix's
   ingest key).
4. Writes the demo operator config and identities.

Every service runs with a read-only root filesystem, no capabilities and `no-new-privileges`.
Every HTTP port reachable outside the stack has a guard (a bearer key, LiteLLM auth, or Host and
Origin checks). Agents join a separate network that reaches only the ports declared for them.

## Built-in services

| Service | Runs | Gives |
|---|---|---|
| `service/postgres-pgvector@1.1.0` | PostgreSQL 16 with pgvector | a URL per database, each with its own role; least-privilege `roles` with nothing but their own schema until `init_sql` grants more |
| `service/litellm@1.0.0` | the LiteLLM proxy as the model gateway | its URL; a master key only AgentBreeder uses |
| `service/phoenix@1.0.0` | Arize Phoenix with auth on, data in Postgres | its URL; an ingest key only services may hold |

Projects add their own versions under `registry/service/`, from a digest-pinned image or built
from source with a strict Dockerfile subset.

### Built-in MCP servers

Each `mcp:` entry in `stack.yaml` runs behind its own relay, which holds the credential. Both
built-ins are verified live through a real `deploy` (2026-11-09):

| Ref | Upstream | Tools |
|---|---|---|
| `mcp/github@1.0.0` | GitHub's hosted MCP server, with a fine-grained token from `GITHUB_MCP_TOKEN` | `get_me`, `list_issues`, `issue_read`, `search_repositories`, `get_file_contents` (read-only) |
| `mcp/playwright@1.0.0` | headless Chromium in `service/playwright-mcp@1.0.0`, reachable only by its relay | `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_close` |

A granted GitHub tool reaches every repository the token can see, so scope the token narrowly.
The browser has no egress until the filtering forward proxy ships, so it can't browse the web
yet. Chromium's own sandbox is off (it can't start without container capabilities), so the
container hardening and the missing egress are the boundary.

## Limits

- Local Docker only; demo identities come from a generated static provider.
- A deployed agent's endpoint is not authenticated.
- MCP relay: it holds the upstream credential and forwards only granted, pinned tools, but tool
  arguments are unconstrained, results reach the agent unfiltered, and it is not policy
  enforcement. A deployed agent's calls through it are verified against the built-in
  `mcp/github` and `mcp/playwright` with a scripted fake gateway, not with a real model.
- `mcp/playwright` has no egress yet: its browser opens pages the agent supplies, not the web.
  Every customer of a deployment shares one browser.
