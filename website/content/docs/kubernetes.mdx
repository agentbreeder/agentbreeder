`agentbreeder promote` deploys the image a release evaluated, by digest, to a local `kind` cluster.

```sh
agentbreeder release agent.yaml --stack . --environment dev            # local Docker first
agentbreeder cluster up --stack . --environment dev --yes              # needs kind >= 0.33 and kubectl
agentbreeder promote agent.yaml --stack . --environment dev --to kubernetes
agentbreeder forward ID --stack . --environment dev                    # loopback port to the pod
agentbreeder logs ID --stack . --environment dev
agentbreeder remove ID --cluster --stack . --environment dev
agentbreeder cluster down --stack .
```

`promote` deploys the image `release` evaluated, by digest, through the same identity gate, then
runs the eval set against the cluster deployment. `deploy` and `remove` take `--local` or
`--cluster`, matching the manifest's target.

## What the deployer enforces

- A dedicated kubeconfig and context; `KUBECONFIG` and `current-context` are ignored. It must be
  private, use static credentials and point at a loopback API server.
- A labelled namespace that enforces the `restricted` Pod Security level.
- The agent runs as UID 65532 with a read-only root filesystem, no capabilities, resource limits
  and no service account token. Secrets go to `kubectl` on stdin. Images are referenced by digest.
- `mcp_access` and runtime enforcement are refused rather than weakened.

On the 2026-11-10 run, network policy blocked the agent pod from the API server, the kubelet and
the local registry, and blocked other pods from the agent. A privileged pod was refused, no
secret value was found in the Deployment, logs or `docker inspect`, `remove` left no labelled
object and revoked the gateway key, and the kill switch stopped both targets.

## Limits

- The stack's services stay in Docker; the `kind` node joins the stack's agents network, which
  exposes its API server and kubelet ports to agents there (both require credentials).
- The local registry on `127.0.0.1:5001` is unauthenticated, and Secrets are unencrypted in
  `kind`'s etcd.
- `kubectl port-forward` is the only way in. There is no public endpoint.
- One `kind` cluster per machine.

## On main, coming in 3.0.0a4

Not in a published package, and **none of it has run on a production or managed cluster**.

- **Kit runtimes on `kind`.** The LangGraph, OpenAI Agents SDK, Deep Agents and CrewAI runtimes
  get a default-deny NetworkPolicy (cluster DNS and the stack's agents network only). Northwind on
  each passed 61/61 on `kind` ([Frameworks and runtimes](/docs/runtimes)).
- **Restricted accounts and admission policies** (written and unit-tested; not yet run on
  `kind` from `main`). `cluster up --restricted` (local `kind` only) is built to install separate
  service accounts with narrow Roles, and `ValidatingAdmissionPolicy` objects meant to admit only
  the objects AgentBreeder writes; deploys then use a restricted deployer account. `cluster policy
  print` and `cluster rbac print` show them without changing anything.
- **A provider interface and the `token` provider** (unit-tested; not yet run on `kind` from
  `main`). Each cluster deployment records which
  provider and cluster it was made on. `cluster connect token` checks an existing cluster reached
  with short-lived service account tokens, then refuses (`KUBERNETES_POLICY_UNCHECKED`) and
  records nothing, because the admission policy check it needs is not wired in yet. Deploying to
  such a cluster is refused the same way.
- **`services render --cluster`** writes a Helm chart for the stack's services, hardened for the
  `restricted` Pod Security level, and refuses a chart that would contain a secret value. It has
  never been installed, and `helm lint` has not been run on its output.

This shows the deployer working; it is not a production design. Helm, external secret stores and
real-cluster certification are tracked in
[#770](https://github.com/agentbreeder/agentbreeder/issues/770). In the
[console](/docs/command-center), **Connect local cluster** and **Deploy to cluster** run the same
commands.
