AgentBreeder is being rebuilt around deploying **existing** agents into infrastructure you
control. You bring a trusted HTTP container; AgentBreeder validates a small manifest, checks the
agent's identity, and deploys it.

**Start here:** [Install](/docs/install) and run `quickstart`, then
[Your own agent](/docs/your-own-agent): write an agent in `agent.yaml`, start its services, test
it, release it through an eval gate and call it.

## What works today

- **Manifest validation.** `agentbreeder validate` checks a strict YAML manifest (v1 or v2). See
  [Manifest](/docs/manifest).
- **Local deployment lifecycle.** Deploy, status and remove on a local Docker engine, with history
  in SQLite. See [Local deployment](/docs/local-deployment).
- **Deploy-time identity gate.** In `enforce` mode a deploy is refused unless the agent already
  exists in your identity provider with an active sponsor, a valid review date and the required
  scoped grants. (`audit` mode records the same denials but lets the deploy proceed.)
  Optional extras: a Cedar, OPA or AuthZEN policy check, second-person approval, a kill switch and
  a hash-chained local audit log. See [Identity gate](/docs/identity-gate).
- **Preview: build agents from `agent.yaml`.** Describe an agent as registry references
  (runtime, prompt, knowledge, tools, evals) and `agentbreeder build` makes the image and the
  deploy manifest. Deploys get local secret files and their own LiteLLM key, and
  `agentbreeder release` promotes only after the eval set passes. Verified only with the Northwind
  example (61/61). See [Build from agent.yaml](/docs/agent-yaml).
- **Preview: local backing services.** `agentbreeder services up` starts the services an agent
  needs from a `stack.yaml` (Postgres with pgvector, a LiteLLM gateway, Phoenix, project services)
  on local Docker and writes a demo operator config. Local only. See
  [Backing services](/docs/services).
- **Opt-in runtime tool enforcement.** Operators can put a deployment behind an MCP egress sidecar
  that applies policy to every MCP Streamable HTTP tool call. STDIO and in-process tools are never
  mediated.

## What isn't implemented

- Production deployment targets. Only the local Docker adapter exists; `kubernetes` is accepted
  by the manifest but not deployable.
- An operational UI or management HTTP API.
- Volumes, in-place updates, and a production secret backend (local secret files only).
- Authenticated invocation: a deployed agent's endpoint trusts whatever caller reaches it.

Verification so far: the local lifecycle, the identity gate (static-file adapter), Cedar policy,
approvals, the kill switch, the audit chain and the MCP egress sidecar pass end to end on macOS with
Docker Desktop (last full run 2026-11-07).
Entra, Keycloak, Okta (experimental) and AWS adapters are fixture-tested; live-tenant checks are
still open. The Linux decision-service socket path is unit-tested but not yet verified on a Linux
host.

## Install

Requires Python 3.11+ and a running local Docker engine. Use a fresh virtual environment: an older
install exposes the 2.x CLI.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install "agentbreeder[eval]==3.0.0a2"
.venv/bin/agentbreeder quickstart
```

[Install](/docs/install) covers uvx and npx, what has been verified on each platform, and installing
with hashes. The demo has been run on macOS; on Linux only the install and `doctor` have been
checked.

The demo builds a sample image, deploys it, invokes it, retries the same deployment, checks the
saved history and removes the container. It needs no model account or API key. The sample echoes
JSON; it is not an AI agent.

If it stops, run `.venv/bin/agentbreeder doctor` first.

For policy checks with Cedar, add the extra: `pip install "agentbreeder[eval,cedar]==3.0.0a2"`. Configuring any policy
engine also requires a verified deployer (an OIDC token from an operator-trusted issuer); the
unverified OS user is then denied with `DEPLOYER_UNVERIFIED`.
