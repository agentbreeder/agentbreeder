AgentBreeder gives agents two ways to call each other:

1. **The A2A registry + invoke API** — register any agent endpoint, then call it by name through the
   AgentBreeder API.
2. **The sidecar A2A forwarder** — an agent posts a JSON-RPC 2.0 request to its local sidecar, which
   forwards it to a configured peer that speaks the [A2A protocol](https://github.com/google/a2a).

<Callout type="warn" title="What is not provided">
  AgentBreeder agents do not serve an A2A JSON-RPC endpoint themselves, and `agent.yaml` has no
  `subagents:` field. Agent runtimes expose the HTTP `/invoke` contract described in the
  [runtime contract](runtime-contract).
</Callout>

## The A2A registry

The registry stores named agent endpoints so other agents and services can find and call them.

```bash
# Register an agent endpoint
curl -X POST https://your-agentbreeder/api/v1/a2a/agents \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "summarizer",
    "endpoint_url": "https://summarizer.run.app",
    "capabilities": ["summarize"],
    "team": "engineering"
  }'

# List registered agents
curl https://your-agentbreeder/api/v1/a2a/agents \
  -H "Authorization: Bearer $TOKEN"
```

| Endpoint | Purpose |
|----------|---------|
| `GET /api/v1/a2a/agents` | List registered agents |
| `GET /api/v1/a2a/agents/{id}` | Get one agent |
| `POST /api/v1/a2a/agents` | Register an agent |
| `PUT /api/v1/a2a/agents/{id}` | Update an agent |
| `DELETE /api/v1/a2a/agents/{id}` | Remove an agent |

The **A2A Agents** page in Studio lists the same registry.

## Invoking a registered agent

`POST /api/v1/a2a/invoke?agent_name=<name>` looks the agent up in the registry and POSTs the message to
its `/invoke` endpoint. The caller needs the `deployer` role.

```bash
curl -X POST "https://your-agentbreeder/api/v1/a2a/invoke?agent_name=summarizer" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "input_message": "Summarise this contract: ...",
    "context": {"session_id": "sess-abc123"}
  }'
```

```json
{
  "data": {
    "output": "Key points: ...",
    "tokens": 312,
    "latency_ms": 1840,
    "status": "success",
    "error": null
  }
}
```

From Python, the same call is available through `engine.a2a.AgentInvocationClient`:

```python
from engine.a2a import AgentInvocationClient

client = AgentInvocationClient(timeout=30.0)
result = await client.invoke(
    endpoint_url="https://summarizer.run.app",
    input_message="Summarise this contract: ...",
)
print(result.output, result.tokens, result.latency_ms)
await client.close()
```

## Forwarding to external A2A servers (sidecar)

Agents deployed with the [sidecar](sidecar) can reach external A2A servers through a localhost helper.
Configure peers in the sidecar's `a2a_peers` map (name → base URL); the sidecar posts JSON-RPC requests
to `<peer URL>/a2a`.

```bash
curl -X POST http://127.0.0.1:9090/a2a/research-agent \
  -H "Content-Type: application/json" \
  -d '{"method": "tasks/send", "params": {"message": "Find recent papers on ..."}}'
```

The peer must implement the A2A JSON-RPC protocol — for example an agent built on a framework that
ships an A2A server.

## A2A vs direct `/invoke`

| | A2A registry + invoke API | Direct `/invoke` |
|--|---------------------------|------------------|
| **Discovery** | By name from the registry | You must know the URL |
| **Auth** | Your AgentBreeder token + `deployer` role | Whatever the agent requires |
| **Use when** | Calling agents registered by other teams | Calling an agent you own |
