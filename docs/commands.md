# Focused rebuild reference

To use the published preview, install `"agentbreeder[eval]==3.0.0a2"` from PyPI (pip or uvx) or run `npx agentbreeder@3.0.0-alpha.2`; a bare `pip install agentbreeder` installs 2.x. `npx` and `uvx` leave no `agentbreeder` command on `PATH`; `uv tool install "agentbreeder[eval]==3.0.0a2"` adds one. See the root README. For development, use a fresh virtual environment in a checkout and install `python -m pip install -e ".[dev]"`. Run `agentbreeder --help`, `agentbreeder validate src/agentbreeder/examples/http-agent/agent.yaml`, `agentbreeder doctor`, `python -m pytest`, `ruff check src tests`, and `python -m build`. Implemented commands: `validate`, `doctor`, `deploy MANIFEST --local --environment ENV` (needs an operator config; see `identity-gate.md` and `first-deployment.md`), `status ID`, `remove ID --local`, `approve`/`reject`, `approve-call`/`reject-call`, `disable`/`enable`, `reconcile --local`, `audit list`/`audit verify`, `login`, `secret set NAME [--from-env VAR [--env-file FILE] | --generate [--force]]` (local secret files, see `local-deployment.md`), `registry new|publish|list|verify` and, on `main` (not in a published preview), the read-only `registry show`, `registry diff` and `registry used-by` (see `registry.md`), `quickstart [--dry-run]` (builds the shipped `http-agent` sample from a copy, passes it through a demo static-adapter identity gate, deploys, invokes, redeploys and removes it; history stays in a printed temporary directory; `--dry-run` runs `doctor` and `validate` only), `example list` and `example NAME [DIR]` (copy a shipped example, default `./NAME`; the copy is checked against the package's `_content.json`, and local state beside a checkout's examples is never copied), `validate` of agent files and of a `stack.yaml` (schema only; `services up` checks references), and `build`, `eval` and `release` (see `agent-yaml.md`). Local-only preview (#734): `services up|status|logs|env|down` start a project's `stack.yaml` backing services with Docker Compose and write a demo operator config under `~/.agentbreeder/stacks/` (see `services.md`); `--stack DIR` on `build`, `deploy`, `eval`, `release`, `status`, `remove` and `reconcile` uses it. `services up DIR --environment ENV [--locked | --update] [--env-file FILE] [--yes]` shows the grant and needs `--yes` when it is new or changed (`--update` accepts new hashes for edited project files such as an `init_sql`, never for a published service version); `services down [--volumes | --purge] --yes` deletes the stack's volumes, or with `--purge` everything `up` made (volumes, built service images, generated secrets, operator config and history). `doctor` also reports whether Compose v2 supports `up --wait` (a warning, not a failure). It also prints an INFO line when it finds 2.x state in `~/.agentbreeder` (names such as `state.json`, `workspace.yaml`, `registry/`; listed, never read); 3.x does not read or change it. Verified end to end with `src/agentbreeder/examples/northwind` (built-in `postgres-pgvector`, `litellm` and `phoenix`, two project services built from source, least-privilege database roles for the agent and the ops service; release 61/61, 2026-11-08 from a checkout and 2026-11-10 from PyPI `3.0.0a1`). `list` opens the local state read-only (no directory or database is created, no migration, no write lock, so it never blocks a running job); when the state is from an older version or an interrupted write left a journal, it says to run `agentbreeder migrate [--state-dir DIR | --stack DIR [--environment ENV]]`, which only upgrades the local state (no identity-provider calls; `status` re-verifies at the IdP and is not a substitute). `--stack DIR` no longer creates a stack directory for a stack that was never brought up (on `main`, not in a published preview). `logs --failed NAME [--state-dir DIR | --stack DIR [--environment ENV]] [--raw] [--json]` prints the redacted log tail `release` saved from its last failed candidate (see `agent-yaml.md`); it reads only that file. `logs ID [--tail N] [--since D] [--follow] [--raw] [--json] [--state-dir DIR | --stack DIR [--environment ENV]]` prints a local deployment's container logs (stdout and stderr, timestamped; `--tail` default 200, at most 10 000; a 4 MiB cap) after Docker confirms the container is the recorded one, with every line redacted (the stack's stored secrets, every non-removed deployment's secret copies, `<state>/secrets`, URL passwords; Docker's 16 KiB partial records of a long line are joined first; best effort: a value transformed another way is not found, and values under 4 characters are not redacted; a value in a line over 16 KiB can be missed when the other stream's output lands between that line's parts) and nothing printed if a value could not be read, including when a deployment's secret copies are gone after a failed deploy (this also refuses a deployment with `model_access` whose gateway mints no per-deployment keys); controls are shown as visible escapes unless `--raw`. Logs can still contain customer messages and model output. `--follow` streams until the container stops, Ctrl-C, SIGTERM, SIGHUP or, when stdin is not a terminal, the end of stdin (so `< /dev/null` ends it at once, with "Follow ended: stdin ended"), and stops its `docker logs` child (a SIGKILL of the CLI alone leaves it until its next write); a line over 1 MiB is dropped whole. `--follow --json` prints one JSON object per line (`schema_version`, `source`, `name`, `deployment`, `line`) and ends with `{"event": "end", "reason": "container|stdin|signal|interrupt", "dropped"}`, or with a one-line error object when `docker logs` failed. For a Kubernetes (local `kind`) deployment, `logs ID` reads the `agent` container of one pod owned by the verified Deployment (through its ReplicaSets' owner references; a pod that merely carries the label is ignored), preferring a running pod, then the newest, with `kubectl logs pod/NAME -c agent`, through the cluster binding recorded with the deployment and after the same cluster, namespace and ownership checks (the pod lookup is scoped by the deployment's label; kubectl's stderr is never shown). A pod with no output yet returns no lines and its reason (a fixed Kubernetes word such as `ImagePullBackOff` or `Unschedulable`; `pod_reason` in `--json`, which also carries `target` and `previous` for both targets); a crash-looping pod is read and its reason shown; `--previous` shows the container before the last restart; `--follow` reads the chosen pod and ends when that pod goes away (`KUBECTL_LOGS_FAILED` when kubectl fails, `POD_NOT_RUNNING` when the pod has no output yet). The Kubernetes target runs no sidecar or egress container, so the agent container is the only source; only local single-user `kind` is supported. Errors are `[CODE] message`, with `--json` also a JSON error object (on `main`, not in a published preview). `services logs` now uses the same redactor (literal, base64, URL-quoted and JSON-escaped forms, URL passwords) and also redacts the stack's deployments' secret copies (on `main`, not in a published preview). `services logs [DIR] NAME [--tail N] [--since D] [--follow] [--json] [--raw]` reads a stack service with `docker compose logs --no-color --no-log-prefix --timestamps` (`--tail` default 200, at most 10 000; a 4 MiB cap), joins Docker's 16 KiB partial records, redacts every line and prints nothing when a value it needs cannot be read (`REDACTION_INCOMPLETE`, as `logs ID`); controls are shown as visible escapes unless `--raw`. `--json` prints `{"schema_version": 1, "source": "service", "target": "local", "name", "lines", "truncated"}`, the same shape as `logs ID`, and `--follow` streams with the same stop rules, NDJSON lines (`source`, `target`, `name`, `line`) and end record. Lines start with Docker's timestamp (no `name |` prefix). A follow carries on across the service's container restarts and stops compose and its plugin together. Errors are coded (`DOCKER_LOGS_FAILED` when compose cannot read the logs), with the JSON error object under `--json`; compose's own stderr is never shown (on `main`, not in a published preview). `logs ID` and `services logs` take `--level warning|error` to keep only records at that level or above, read per known format keyed by built-in ref (`service/postgres-pgvector`, including `FATAL` and `PANIC`; `service/litellm`; `service/phoenix`; `runtime/adk`) from `stack.lock` for a service and, for a deployment, from `--stack DIR`'s `deploy/NAME.build.json` when it records the runtime as built-in. A record's continuation lines (a traceback, Postgres `DETAIL`/`STATEMENT`, a multi-line SQL statement) keep its level, and a blank line ends a record unless the next line clearly continues it. It is a heuristic: project services, MCP relays and other images are unclassified, and `--level` on them fails with `LEVELS_UNAVAILABLE`. A container decides what its own lines look like, so `--level` can hide lines: it is a reading aid, not a completeness guarantee (hidden lines are redacted all the same). `--json` adds `format`, `levels` (one per line, null when unclassified) and `level`; `--follow --json` adds each line's `level` (on `main`, not in a published preview). `doctor` also checks, as advice only (never a failure), that the `agentbreeder` on `PATH` is this version: none is expected with npx or uvx (uv's temporary environment is skipped, so a stale install behind it is found), and a stale one from another install is named with the command to use instead. `cluster up` and `cluster down` hold a per-user lock (`~/.agentbreeder/locks/cluster.lock`, independent of `AGENTBREEDER_STACKS_DIR`); a second one at the same time fails with `CLUSTER_BUSY` (on `main`, not in a published preview). Commands that end a step print a `Next:` line in the form you launched with (`agentbreeder`, `npx agentbreeder@<ver>`, `uvx --from 'agentbreeder[eval]==<ver>' agentbreeder` or `python -m agentbreeder`), with the `--stack` and `--environment` they used; `build` points at `release`, never at a production `deploy` (on `main`, not in a published preview). `next [DIR] [--environment ENV] [--output DIR] [--json]` shows where a project is on the guided path and the one command to run next, reading only (state opened read-only, `DIR`'s stack state, one `compose ps`, no key values); text exits 1 while steps remain, `--json` prints the `next.md` contract and exits 0 (on `main`, not in a published preview). `new agent NAME --model gemini [--dir DIR] [--dry-run] [--json]` writes a starter project to `DIR` (default `./NAME`; it must not exist, or be an empty directory you own that others cannot write to, never a symlink): `agent.yaml` (`runtime/adk@1.0.6`, `traces: none`, `agent_events: none`, and a comment on the edit loop), `stack.yaml` (Postgres and LiteLLM, `chat` and `judge` aliases, a `DATABASE_URL` binding, `candidate: true`, `review_by` 180 days from today), `stack/litellm/config.yaml`, and the editable sources `src/prompt/` and `src/evals/` (the two eval cases run on 3.0.0a2, `retries: 1`); it publishes `prompt/NAME-prompt@0.1.0` and `eval/NAME-evals@0.1.0` into `DIR/registry` and writes `agent.lock`, so `build --locked` passes. Files are 0644 and directories 0755; on failure it removes what it wrote. `--model` is required and only `gemini` is offered (the only provider run end to end). `--dry-run` writes nothing; `--json` prints the files (path, mode, hash) and the published refs, and on a refusal `{"schema_version": 1, "error": {"code", "message"}}` (exit 2; argparse usage errors stay plain text). A group-writable existing `DIR` is accepted only off macOS and only for your own group. The template ran once end to end from a checkout on macOS (2026-11-12, `release` 2/2). To change the prompt: edit `src/prompt/prompt.md`, bump `version:` in `src/prompt/manifest.yaml`, `registry publish src/prompt`, change the ref in `agent.yaml`, then `build` and `release`. `quickstart` now ends with `Next: … new agent hello --model gemini`, and `next` offers `new agent` for a directory without `agent.yaml` (on `main`, not in a published preview). `invoke NAME MESSAGE|- [--candidate] [--customer ID] [--session ID] [--json] [--state-dir DIR | --stack DIR [--environment ENV]]` sends one message to a ready local deployment and prints its reply: only `http://127.0.0.1:<port>` endpoints from local state (Kubernetes rows are refused; use `forward`), after Docker confirms the container is the recorded one and still publishes that port; no proxies, no redirects, one 180 s deadline for the whole exchange, state opened read-only. Controls in the reply are shown as visible escapes; `--json` prints the whole answer. `--candidate` calls `NAME-candidate`; `--customer`/`--session` are not authenticated (#780). A message given as an argument is visible to other local users in `ps`; pass `-` to read it from stdin. Exit 0 with a reply; 1 when the message was (or may have been) sent but no usable reply came back (a retry is a second turn); 2 when nothing was sent. Errors are `[CODE] message` on stderr, and with `--json` also `{"schema_version": 1, "error": {"code", "message", "sent"}}` on stdout; printed follow-ups carry the same `--stack` or `--state-dir` (on `main`, not in a published preview). `your-first-agent.md` walks from an empty directory to a released starter agent and an `invoke` reply with the steps and commands `next` uses; a test keeps the page, `guide.py` and `guide_checks.py` in step (on `main`, not in a published preview). `watch --stack DIR [--json]` reports one stack's container events until stopped, reading only (the stack state and every environment's deployment state opened read-only; one `docker events` child for container events): `died` when a container exits by itself (a `die` with no `kill` or `stop` for it since it last started, so a stop, `docker kill`, `remove`, a release or `services down` reports nothing; an agent container whose deployment is not `ready` is the running job's and reports nothing either; `exit_code` and `oom`), `unhealthy` when a health check starts failing, and `restarted` when a container that died starts again (the CLI cannot see the console's jobs, so the console drops `restarted` while its own `services up` runs). Stack services match by the stack label (one-shot `init` and `bootstrap` steps are skipped), agent containers by this stack's deployment IDs. It prints a `status` record (`services` from one `docker compose ps`, null when compose could not be read; `deployments` with `id`, `name`, `target` and `state`, and for a ready Kubernetes (local `kind`) deployment a `pod` check, `running` and `reason`) at the start and every 60 s; container events cover local targets only. `--json` prints one object per line (`schema_version`, `event`, `time`, `source`, `name`, `deployment`, and `role` for a sidecar) and ends with `{"event": "end", "reason": "stdin|signal|interrupt", "dropped"}` (`dropped` counts records lost when more than 1 000 were waiting). The status is read on a worker thread, so a stop never waits for `compose ps` or kubectl, and `docker events` runs with the same scrubbed environment as every other docker call. Labels are not authenticated: a container on the same Docker engine can claim this stack's labels, so events are best effort. It stops, with its `docker events` child, on the end of a non-terminal stdin, SIGTERM, SIGHUP or Ctrl-C, as `logs --follow` does; if `docker events` ends by itself it fails with `DOCKER_EVENTS_FAILED`. Events are not stored (on `main`, not in a published preview). `services usage [DIR] [--follow] [--json]` shows one stack's resource use, reading only: its containers are matched as `watch` matches them (stack services by label, agent containers by this stack's deployment IDs) and listed again every 10 s, and one streaming `docker stats` child runs over exactly those container IDs (replaced when the set changes; no child at all when nothing is running). `--json` prints one object per line, each with `schema_version` and `event`: `sample` (`time`, `containers` with `source`, `name`, `deployment`, `role` for a sidecar, `cpu_percent`, `memory_used`, `memory_limit`, `memory_percent`, `network_rx`, `network_tx`, `block_read`, `block_write` and `pids`; bytes as integers, null where Docker has no value), at most one every 2 s; `disk` (`as_of`, `stale`, `volumes` with `name` and `size`, `containers` with their writable-layer `size`) from `docker system df -v` every 60 s, read on a worker thread and cached, so `as_of` says how old it is and `stale` that the latest reading failed; and, when it is stopped, the end record `{"event": "end", "reason": "stdin|signal|interrupt", "dropped"}`. CPU and memory are of the Docker VM on Docker Desktop. Without `--follow` it prints one sample and one disk reading and exits (`DOCKER_STATS_FAILED` if they do not come within 30 s). `--follow` stops, with its `docker stats` child, on the end of a non-terminal stdin, SIGTERM, SIGHUP or Ctrl-C (`docker stats` ignores SIGTERM, so it is killed). `docker stats` exits at once when a listed container is already gone, so a child that ends is replaced after a new listing; when three in a row end, or the containers cannot be listed three times in a row, it fails with `DOCKER_STATS_FAILED`. Docker's container names, labels and mounts are never printed; labels are not authenticated, so usage is best effort (on `main`, not in a published preview). When the terminal's Ctrl-C or a SIGTERM/SIGHUP for the whole process group reaches the docker or kubectl child of `logs --follow`, `services logs --follow`, `watch` or `services usage --follow` first, the child's exit (killed by the signal, or 130, 143 or 129 when it caught it) ends the command like the signal itself: the end record's reason is `interrupt` or `signal`, exit 0. On Docker 27.5, `docker compose logs -f` exits 130 after SIGINT and SIGTERM, while `docker logs -f` and `docker events` exit 1, which still reads as a failure in that race; kubectl was not checked. The CLI's own handler usually records the stop first (on `main`, not in a published preview). Run `agentbreeder COMMAND --help` for flags; see the root README for the demo.
