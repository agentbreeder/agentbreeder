# `agentbreeder new`

Write a starter project (`new agent NAME`).

`new agent NAME --model gemini|anthropic|openai|openrouter [--model-id ID] [--dir DIR] [--dry-run] [--json]` writes a starter project to `DIR` (default `./NAME`; it must not exist, or be an empty directory you own that others cannot write to, never a symlink): `agent.yaml` (`runtime/adk@1.2.0`, `1.0.6` before #828, `traces: none`, `agent_events: none`, and a comment on the edit loop), `stack.yaml` (Postgres and LiteLLM, `chat` and `judge` aliases, a `DATABASE_URL` binding, `candidate: true`, `review_by` 180 days from today), `stack/litellm/config.yaml`, and the editable sources `src/prompt/` and `src/evals/` (the two eval cases run on 3.0.0a2, `retries: 1`); it publishes `prompt/NAME-prompt@0.1.0` and `eval/NAME-evals@0.1.0` into `DIR/registry` and writes `agent.lock`, so `build --locked` passes. Files are 0644 and directories 0755; on failure it removes what it wrote.

`--model` is required. On `main`, not in a published preview (#905): `anthropic` (default `anthropic/claude-opus-5-5`), `openai` (default `openai/gpt-5.6`) and `openrouter` (no default: `--model-id openrouter/<vendor>/<model>` is required) are offered beside `gemini` (`gemini/gemini-3.8-flash`); every gateway alias calls the one model through LiteLLM, which reads the key (`GEMINI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` or `OPENROUTER_API_KEY`) from the stack's local secret file, never from YAML. `--model-id PROVIDER/…` replaces the default (letters, digits and `._:/-`, at most 128 characters, no empty segment; anything else is `MODEL_ID_INVALID` and is not echoed). Only `gemini` has been run end to end; `anthropic`, `openai` and `openrouter` are config-only, not run end to end (the eval judge needs strict `json_schema` output, unverified on them), and the text output says so. `--json` adds `model_id` and `verified`. `--stack-for` takes the same `--model` and `--model-id`. `next` reports the chosen provider's missing key as `KEYS_MISSING` with its key page. `--model gemini` without `--model-id` writes the same files as before. `--dry-run` writes nothing; `--json` prints the files (path, mode, hash) and the published refs, and on a refusal `{"schema_version": 1, "error": {"code", "message"}}` (exit 2; argparse usage errors stay plain text). A group-writable existing `DIR` is accepted only off macOS and only for your own group.

The template ran once end to end from a checkout on macOS (2026-11-12, `release` 2/2).

To change the prompt: edit `src/prompt/prompt.md`, bump `version:` in `src/prompt/manifest.yaml`, `registry publish src/prompt`, change the ref in `agent.yaml`, then `build` and `release`.

`new agent NAME --model PROVIDER [--model-id ID] --stack-for DIR/agent.yaml [--dry-run] [--json]` onboards an existing `agent.yaml` alone: it writes only `stack.yaml` and `stack/litellm/config.yaml` beside it (neither may exist; nothing else in the project changes), the starter's stack with one gateway alias per model the agent uses (its `model.alias` and its eval set's `judge.alias`, which must resolve from the project's registry or the built-ins) and ceilings of at least the agent's own `budget_usd` and `rpm` (5 USD and 60 rpm otherwise), so the gate does not refuse its deploys. `NAME` must be the agent's `name`. An agent with `knowledge`, `tools` or `mcp` is refused (`STACK_FOR_UNSUPPORTED`: those need services this stack does not have; write `stack.yaml` by hand, see `services.md`), as is an alias other than letters, digits, `.`, `_` and `-` (`ALIAS_UNSUPPORTED`); `traces: otlp` gets a warning, since the stack has no trace collector. The directory and `agent.yaml` must be yours and not writable by others, and so must every ancestor (yours or root's; a sticky directory such as `/tmp` is allowed), the check console registration applies (`PROJECT_UNSAFE`). Files are staged, validated and hard-linked into place (an existing file is never replaced); on failure what it created is removed. `--json` prints `agent_file`, `aliases`, `model_id`, `verified`, `files` (path, mode, hash) and `warnings`; refusals have the same error object. On `main`, not in a published preview (#823, for the console's onboarding confirm): `--json` also prints `agent_sha256` (the digest of the `agent.yaml` that was read), `refs` (every registry ref in `agent.yaml`, each `{ref, kind, root_kind, runs_code}`: `root_kind` is `project`, `path` or `builtin`, `runs_code` is true for `tool`, `service`, `eval`, `mcp` and `runtime`) and `runs_code` (true when a code ref resolves outside the built-in registry); an unresolvable ref is refused with the registry's code (`REF_NOT_FOUND`). The text output names those code refs. `--expect-digest sha256:…` (only with `--stack-for`; `USAGE` otherwise, `DIGEST_INVALID` if malformed) refuses with `DIGEST_MISMATCH` unless `agent.yaml` still has the previewed digest, and the write refuses with `AGENT_CHANGED` if the file changes while it is read or after it was checked. For the starter's own `agent.yaml` it writes the starter's stack (a test checks this); onboarding has not yet been run end to end with `services up` and `release` (on `main`, not in a published preview).

`new agent NAME --from-spec FILE [--dir DIR] [--dry-run] [--json]` (on `main`, not in a published preview; #833, the CLI half of the console's agent builder) writes a project from a JSON spec instead of the starter's text. `FILE` must be a regular file (not a link) that you own and no other user can read or write (`chmod 600`: it holds a prompt), at most 256 KiB of UTF-8 JSON with no duplicate keys or non-finite numbers (`SPEC_UNSAFE`, `SPEC_TOO_LARGE`, `SPEC_INVALID`, `SPEC_MISSING`). `--model`, `--model-id` and `--stack-for` are refused with it (`USAGE`); without `--from-spec`, `--model` is required (`USAGE`). The spec, `schema_version` 1 (others are `SPEC_VERSION_UNSUPPORTED`; unknown fields are `SPEC_INVALID`):

```json
{
  "schema_version": 1,
  "name": "helper",
  "model": "gemini",
  "model_id": null,
  "max_model_calls": 2,
  "prompt": {"text": "You are helper, ..."},
  "evals": {
    "cases": [{"id": "hours", "turns": ["When is support open?"],
               "expect": {"must_match": ["9"]}, "reference": "9am to 5pm Pacific."}],
    "threshold": 1.0,
    "retries": 1
  },
  "tools": ["tool/echo@0.1.0"],
  "knowledge": [],
  "mcp": [{"ref": "mcp/github@1.0.0", "tools": ["get_me"]}]
}
```

`name` must be `NAME` (`NAME_MISMATCH`) and passes the starter's name check; `model` and `model_id` are `--model` and `--model-id`. The prompt is at most 32 KiB; prompt, turns (1–10 per case) and references have no control or bidi characters but tab and newline (a carriage return is refused, so use `\n` line ends). Cases (1–100, unique `id`s) take `expect` keys `must_match`, `must_not_match` (regular expressions of at most 200 bytes, with at most two variable repeats (`?`, `*`, `+`, `{m,n}`) and alternations (`|`) together, and no nested repeats, repeated alternatives or backreferences, the shapes that can backtrack for minutes on a reply), `tools_include` and `tools_exclude`. `tools` and `mcp` refs must resolve over the roots the new project resolves, the built-ins and `AGENTBREEDER_REGISTRY_PATH` (the registry's code otherwise, e.g. `REF_NOT_FOUND`), one version per name; they are not copied into the project, and `agent.lock` records where each came from (a path relative to the project). Each MCP server's tools must be declared by its version (`MCP_TOOL_UNDECLARED`). Any `knowledge` entry is refused for now (`SPEC_UNSUPPORTED`): the generated stack has no embedding model or index.

The project is the starter's shape: `agent.yaml` (with `tools:` and `mcp:` entries), the prompt and the cases as `src/prompt/` and `src/evals/`, published as `prompt/NAME-prompt@0.1.0` and `eval/NAME-evals@0.1.0` into `DIR/registry`, the `--stack-for` stack (`chat` and `judge` aliases, 5 USD and 60 rpm) with an `mcp:` entry per server named after its ref, each server's tools granted to the agent as `mcp grant` would (`environment.agents.NAME.mcp`), and `agent.lock`. The same destination rules, staging and rollback as the starter apply. `--json` prints the starter's summary plus, for each file, its full text in `content` (the console's preview shows this, never YAML of its own), `spec_version`, `combination` (`parts`, and `verified`: true only for a combination run end to end, today model + prompt + evals with `gemini`), `refs` (`{ref, kind, root_kind, runs_code, sha256}`, the version's content digest), `runs_code`, `grants` (`[{server, tools}]`), `keys` (the model key and each MCP server's imported keys) and `plan_sha256` (the digest of every file's text, the refs and the destination). The write also refuses (`DIGEST_MISMATCH`) a picked version whose content changed before `agent.lock` was written. `--expect-digest sha256:…` refuses the write with `DIGEST_MISMATCH` unless the plan is still the previewed one (the spec, a picked version or the date changed), `DIGEST_INVALID` if malformed. A dry run also loads the generated stack and reviews its gateway config, as the write does. Unverified combinations are written too; the text output says they have not been run end to end, and names code refs from outside the built-ins. Not yet run end to end with `services up` and `release`.

Flags: `agentbreeder new --help`.
