# `agentbreeder new`

Write a starter project (`new agent NAME`).

`new agent NAME --model gemini|anthropic|ollama|openai|openrouter [--model-id ID] [--runtime REF] [--dir DIR] [--dry-run] [--json]` writes a starter project to `DIR` (default `./NAME`; it must not exist, or be an empty directory you own that others cannot write to, never a symlink): `agent.yaml` (`runtime/adk@1.4.0` since #1056, `1.3.0` since #1030, `1.2.0` before that; a `--model gemini` starter on `1.4.0` ran `services up` and `release` 2/2 once, 2026-11-16, from a wheel built from the #1056 branch; the other runs named on this page used `1.3.0` or earlier and `1.0.6` before #828, `traces: none`, `agent_events: none`, and a comment on the edit loop), `stack.yaml` (Postgres and LiteLLM, `chat` and `judge` aliases, a `DATABASE_URL` binding, `candidate: true`, `review_by` 180 days from today), `stack/litellm/config.yaml` (on `main`, not in a published preview (#1018): it pins `litellm_settings.turn_off_message_logging: true` and `general_settings.store_prompts_in_spend_logs: false`, as Northwind does, so LiteLLM's spend logs are meant to keep tokens and cost but no prompt or reply; `--stack-for` and `--from-spec` write the same pins; checked once against a running LiteLLM with a `--model gemini` starter from a wheel built from `main` (M4 record, #1040): its 7 spend-log rows kept tokens and cost, `messages`, `response` and `proxy_server_request` were `{}` in every row, and the text sent was not found anywhere in the gateway's database), and the editable sources `src/prompt/` and `src/evals/` (the two eval cases run on 3.0.0a2, `retries: 1`); it publishes `prompt/NAME-prompt@0.1.0` and `eval/NAME-evals@0.1.0` into `DIR/registry` and writes `agent.lock`, so `build --locked` passes. Files are 0644 and directories 0755; on failure it removes what it wrote.

`--runtime runtime/NAME@X.Y.Z` (on `main`, not in a published preview; #1083 F1) pins another runtime version in `agent.yaml` than the default, `runtime/adk@1.4.0`. Without it the starter is byte for byte what it was. The ref must be a pinned `runtime/` ref (`RUNTIME_INVALID` otherwise; the supplied text is not echoed) that resolves from the built-ins or `AGENTBREEDER_REGISTRY_PATH` (the registry's code otherwise, e.g. `REF_NOT_FOUND`; the project's own `registry/` does not exist yet). The version is checked as `build` checks it, before anything is written: a manifest the engine cannot read, or a missing or invalid `runtime/modules.json` (`ARTIFACT_INVALID`), a protocol this AgentBreeder does not know (`PROTOCOL_UNSUPPORTED`), and a capability or limit the starter's `agent.yaml` needs (`build`'s codes). `agent.lock` pins the version that was checked (`DIGEST_MISMATCH` if it changes before the lock is written). Only the default has been run end to end with the starter: with any other version `--json` has `verified: false` and the text output says so, and for a version from `AGENTBREEDER_REGISTRY_PATH` it also says that this is code AgentBreeder does not ship (`--json`: `runtime_root_kind: "path"`, a key that is absent for a built-in). No runtime other than `runtime/adk` exists yet; `agentbreeder registry runtimes` lists what is there. `--runtime` cannot be combined with `--stack-for` (the existing `agent.yaml` pins its runtime) or `--from-spec` (the spec's `runtime` does); both are `USAGE`.

`--model` is required. On `main`, not in a published preview (#905): `anthropic` (default `anthropic/claude-opus-5-5`), `openai` (default `openai/gpt-5.6`) and `openrouter` (default `openrouter/google/gemini-3.8-flash` since #1020, before which `--model-id` was required; its ids are `openrouter/<vendor>/<model>`) are offered beside `gemini` (`gemini/gemini-3.8-flash`); every gateway alias calls the one model through LiteLLM, which reads the key (`GEMINI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` or `OPENROUTER_API_KEY`) from the stack's local secret file, never from YAML. `--model-id PROVIDER/…` replaces the default (letters, digits and `._:/-`, at most 128 characters, no empty segment; anything else is `MODEL_ID_INVALID` and is not echoed). `gemini`, `openrouter` and `openai` have been run end to end with their default models; for `openrouter` and `openai` that is on `main`, not in a published preview (#1020: `services up`, `release` 2/2 with the judge's strict `json_schema` output, then `invoke` 2/2, from a wheel built from `main`; `docs/superpowers/verification/providers.md`). `anthropic` is config-only, not run end to end (the eval judge needs strict `json_schema` output, unverified on it), and the text output says so. `verified` is per provider: it covers the gateway and judge path with the provider's default model, not how well another `--model-id` answers (through OpenRouter, `anthropic/claude-haiku-5.5` ran but failed one of the starter's two eval cases on its answer). With a verified provider and another model id, `verified` stays true and the text output says that only the default model has been run end to end. `--json` adds `model_id` and `verified`. `--stack-for` takes the same `--model` and `--model-id`. `next` reports the chosen provider's missing key as `KEYS_MISSING` with its key page. `--model gemini` without `--model-id` writes the same files as before. On `main`, not in a published preview (#1025 O1): `ollama` (default `ollama_chat/llama3.2:3b`; ids are `ollama_chat/<model>`) needs no key. Its stack names `service/litellm@1.2.0`, both aliases call `api_base: http://host.docker.internal:11434`, `agent.yaml` has `reasoning: none` (llama3.2 refuses Ollama's think option), `--json` has `key: null` and `keys: []`, and the text output says to `ollama pull` the model instead of naming a key file. It has been run end to end on macOS with Docker Desktop only (`services up`, `release` 2/2 with the same model as judge, `invoke`; `docs/superpowers/verification/ollama.md`); Linux has not That run used `runtime/adk@1.3.0`; the starter now writes `1.4.0` (#1056), which has not been run with Ollama. See "Ollama on this machine" in `services.md`. `--from-spec` offers no embedding model for it, so a spec with knowledge is `SPEC_UNSUPPORTED`. `--dry-run` writes nothing; `--json` prints the files (path, mode, hash) and the published refs, and on a refusal `{"schema_version": 1, "error": {"code", "message"}}` (exit 2; argparse usage errors stay plain text). A group-writable existing `DIR` is accepted only off macOS and only for your own group.

The template ran once end to end from a checkout on macOS (2026-11-12, `release` 2/2).

To change the prompt: edit `src/prompt/prompt.md`, bump `version:` in `src/prompt/manifest.yaml`, `registry publish src/prompt`, change the ref in `agent.yaml`, then `build` and `release`.

`new agent NAME --model PROVIDER [--model-id ID] --stack-for DIR/agent.yaml [--dry-run] [--json]` onboards an existing `agent.yaml` alone: it writes only `stack.yaml` and `stack/litellm/config.yaml` beside it (neither may exist; nothing else in the project changes), the starter's stack with one gateway alias per model the agent uses (its `model.alias` and its eval set's `judge.alias`, which must resolve from the project's registry or the built-ins) and ceilings of at least the agent's own `budget_usd` and `rpm` (5 USD and 60 rpm otherwise), so the gate does not refuse its deploys. `NAME` must be the agent's `name`. An agent with `knowledge`, `tools` or `mcp` is refused (`STACK_FOR_UNSUPPORTED`: those need services this stack does not have; write `stack.yaml` by hand, see `services.md`), as is an alias other than letters, digits, `.`, `_` and `-` (`ALIAS_UNSUPPORTED`); `traces: otlp` gets a warning, since the stack has no trace collector. The directory and `agent.yaml` must be yours and not writable by others, and so must every ancestor (yours or root's; a sticky directory such as `/tmp` is allowed), the check console registration applies (`PROJECT_UNSAFE`). Files are staged, validated and hard-linked into place (an existing file is never replaced); on failure what it created is removed. `--json` prints `agent_file`, `aliases`, `model_id`, `verified`, `files` (path, mode, hash) and `warnings`; refusals have the same error object. On `main`, not in a published preview (#823, for the console's onboarding confirm): `--json` also prints `agent_sha256` (the digest of the `agent.yaml` that was read), `refs` (every registry ref in `agent.yaml`, each `{ref, kind, root_kind, runs_code}`: `root_kind` is `project`, `path` or `builtin`, `runs_code` is true for `tool`, `service`, `eval`, `mcp` and `runtime`) and `runs_code` (true when a code ref resolves outside the built-in registry); an unresolvable ref is refused with the registry's code (`REF_NOT_FOUND`). The text output names those code refs. `--expect-digest sha256:…` (only with `--stack-for`; `USAGE` otherwise, `DIGEST_INVALID` if malformed) refuses with `DIGEST_MISMATCH` unless `agent.yaml` still has the previewed digest, and the write refuses with `AGENT_CHANGED` if the file changes while it is read or after it was checked. For the starter's own `agent.yaml` it writes the starter's stack (a test checks this); onboarding has not yet been run end to end with `services up` and `release` (on `main`, not in a published preview).

`new agent NAME --from-spec FILE [--dir DIR] [--dry-run] [--json]` (on `main`, not in a published preview; #833, the CLI half of the console's agent builder) writes a project from a JSON spec instead of the starter's text. `FILE` must be a regular file (not a link) that you own and no other user can read or write (`chmod 600`: it holds a prompt), at most 256 KiB of UTF-8 JSON (512 KiB for a `schema_version` 2 spec) with no duplicate keys or non-finite numbers (`SPEC_UNSAFE`, `SPEC_TOO_LARGE`, `SPEC_INVALID`, `SPEC_MISSING`). `--model`, `--model-id` and `--stack-for` are refused with it (`USAGE`); without `--from-spec`, `--model` is required (`USAGE`). The spec, `schema_version` 1 or 2 (others are `SPEC_VERSION_UNSUPPORTED`; unknown fields are `SPEC_INVALID`; version 2 is below):

```json
{
  "schema_version": 1,
  "name": "helper",
  "model": "gemini",
  "model_id": null,
  "max_model_calls": 2,
  "prompt": {"text": "You are helper, ..."},
  "evals": {
    "cases": [{"id": "hours", "turns": ["When is support open?"],
               "expect": {"must_match": ["9"]}, "reference": "9am to 5pm Pacific."}],
    "threshold": 1.0,
    "retries": 1
  },
  "tools": ["tool/echo@0.1.0"],
  "knowledge": [{"ref": "knowledge/acme-help@1.0.0", "top_k": 5, "extra_searches": 1}],
  "mcp": [{"ref": "mcp/github@1.0.0", "tools": ["get_me"]}]
}
```

`name` must be `NAME` (`NAME_MISMATCH`) and passes the starter's name check; `model` and `model_id` are `--model` and `--model-id`. The prompt is at most 32 KiB; prompt, turns (1–10 per case) and references have no control, bidi or invisible format characters (soft hyphen, zero-width space, BOM, tag characters) but tab, newline and the zero-width joiners (a carriage return is refused, so use `\n` line ends). Cases (1–100, unique `id`s) take `expect` keys `must_match`, `must_not_match` (regular expressions of at most 200 bytes, with at most two variable repeats (`?`, `*`, `+`, `{m,n}`) and alternations (`|`) together, and no nested repeats, repeated alternatives or backreferences, the shapes that can backtrack for minutes on a reply), `tools_include` and `tools_exclude`. `tools` and `mcp` refs must resolve over the roots the new project resolves, the built-ins and `AGENTBREEDER_REGISTRY_PATH` (the registry's code otherwise, e.g. `REF_NOT_FOUND`), one version per name; they are not copied into the project, and `agent.lock` records where each came from (a path relative to the project). Each MCP server's tools must be declared by its version (`MCP_TOOL_UNDECLARED`). `knowledge` (on `main`, not in a published preview; #989) takes at most one entry (the generated stack serves one embedding alias, and `runtime/adk` 1.x retrieves from one set; two are `SPEC_INVALID`, whatever the runtime's own `limits.knowledge`: this one limit stays the builder's). Each entry is `{"ref": "knowledge/NAME@X.Y.Z", "top_k": 1–20 (default 5), "extra_searches": 0–5 (default 1)}`, the fields `agent.yaml` has. Only a pinned registry ref is accepted; it resolves like `tools` (the registry's code otherwise, e.g. `REF_NOT_FOUND`) and is not copied. The runtime embeds with the alias the knowledge version names, so the version's manifest must give an `embedding.alias` of letters, digits, `.`, `_` and `-` (at most 64), other than `chat` or `judge` (`ALIAS_UNSUPPORTED`), and `embedding.dimensions` from 1 to 16000 (default 768); `store`, if given, must be `pgvector`, and `chunking`, if given, `paragraph` (`KNOWLEDGE_INVALID`). More than 50,000 chunks is `KNOWLEDGE_TOO_LARGE`. The stack serves that alias with the provider's embedding model from the pinned LiteLLM 1.106.2 map, with the provider's key and the version's dimensions: `gemini` → `gemini/gemini-embedding-2` (at most 3072 dimensions), `openai` → `openai/text-embedding-3-small` (at most 1536). `anthropic` and `openrouter` have no embedding model there, and larger dimensions are refused too (`SPEC_UNSUPPORTED`). The runtime retrieves once before the first model call; further searches are tool calls, made only in model calls with tools on (all but the last of `max_model_calls`) and never more than `extra_searches` per turn, so `max_model_calls` 1 retrieves but never searches again (the spec's default is 2). A knowledge version's manifest is read only once the registry has checked and hashed it (a link, a hard link or a non-regular file such as a FIFO is refused), and a version that changes while it is read is refused (`DIGEST_MISMATCH`).


**Spec version 2** (on `main`, not in a published preview; #1058 SP, shared with #1085's `runtime`). A version 2 spec may also carry `runtime`, `subagents`, `skills` and `limits`, case `tags`, and the eval checks `subagents_include`, `subagents_exclude`, `subagent_tools_include`, `skills_loaded` and `skills_not_loaded` (`docs/evals.md`). A version 1 spec that carries any of them is `SPEC_INVALID`, naming where (`subagents: needs schema_version 2`). A version 1 spec writes exactly the files it wrote before version 2 existed (a golden test), and a version 2 spec without these fields writes the same files with `spec_version: 2` in `--json`.

```json
{
  "schema_version": 2,
  "runtime": "runtime/adk@1.5.0",
  "subagents": [{"name": "billing", "description": "Refunds and invoices.", "model": "gemini",
                 "model_id": null, "max_model_calls": 4, "max_calls_per_turn": 2,
                 "prompt": {"text": "You are the billing specialist, ..."},
                 "tools": ["tool/echo@0.1.0"], "mcp": [{"ref": "mcp/github@1.0.0", "tools": ["get_me"]}]}],
  "skills": ["skill/refund-policy@1.0.0"],
  "limits": {"turn_model_calls": 12},
  "evals": {"cases": [{"id": "refund-1", "turns": ["Can I get a refund?"], "tags": ["billing"],
                       "expect": {"subagents_include": ["billing"]}, "reference": "..."}]},
  "...": "the version 1 fields"
}
```

- `runtime` is a pinned `runtime/NAME@X.Y.Z` ref, written as `agent.yaml`'s `runtime:` and listed first in `refs`. Without it the project keeps the starter's runtime (`runtime/adk@1.4.0`). A spec that pins another runtime than the starter's is not `verified`, since every verified run used the starter's.
- The runtime must list the capability each part needs in its manifest's `capabilities` (the parser `build` uses). Otherwise the spec is refused before anything is written, with the code `build` would give: `RUNTIME_NO_SUBAGENTS`, `RUNTIME_NO_SKILLS`, `MCP_RUNTIME_UNSUPPORTED` or, since #1083 F1, `RUNTIME_NO_KNOWLEDGE`, `RUNTIME_NO_NOTES` and `RUNTIME_LIMIT` (more tools, MCP servers or knowledge sets than the runtime's `limits`); a runtime whose manifest names a protocol this AgentBreeder does not know is `PROTOCOL_UNSUPPORTED`. A manifest without a `protocol` key (every `runtime/adk` version up to `1.4.0`) is read as before, with `knowledge` and `notes` implied (see [Runtime versions](../registry.md#runtime-versions-on-main-not-in-a-published-preview)). A skill with scripts is also refused (`RUNTIME_NO_SKILL_SCRIPTS`) unless the runtime lists `skill_scripts`, which no runtime does; `build` itself refuses every skill on a runtime without `skills`. `runtime/adk@1.5.0` declares `protocol: 1` and lists `subagents` and `skills` (on `main`, not in a published preview; checked by its runtime tests only), so a spec has to name it in `runtime` to use either; the default runtime does not list them.
- `subagents` (at most 5, names `^[a-z][a-z0-9_]{0,31}$`, unique) take a `description` (at most 500 characters, as the agent's text rules), a `model` and optional `model_id` as the agent's, `max_model_calls` (1–20, default the agent's), `max_calls_per_turn` (1–3, default 2), a `prompt` (at most 32 KiB), `tools` (at most 20 `tool/` refs) and `mcp` entries. Each `mcp` server and tool must also be in the agent's own `mcp` (`SUBAGENT_MCP_UNGRANTED`); `tool/customer-notes` is the agent's only (`SUBAGENT_NOTES`). The agent and its sub-agents have one version per tool name; the same ref in several is placed once. A sub-agent whose name the agent already sees as a tool (`ask_<name>`) is `SUBAGENT_NAME_CLASH`, as `build` refuses it. An `ollama` sub-agent needs an `ollama` agent and the reverse (`SPEC_UNSUPPORTED`: they need different gateway versions).
- Each sub-agent's prompt is written to `src/subagents/SUB/` and published as `prompt/NAME-SUB-prompt@0.1.0` (`_` in `SUB` becomes `-`; a name over 63 characters is `SPEC_INVALID`). A sub-agent on the agent's provider and model id uses the agent's `chat` alias; any other gets its own alias `chat-SUB`, served by the gateway with its provider's key and listed in `environment.models`. `aliases` and `keys` in `--json` include them, and `published` lists the prompt versions.
- `skills` (at most 10 pinned `skill/` refs, one version per name) are written as `agent.yaml`'s `skills:` and listed last in `refs`.
- `limits.turn_model_calls` (1–40) is valid only with `subagents`.
- Case `tags` are at most 5 distinct names (`^[a-z][a-z0-9_-]{0,31}$`). A check that names a sub-agent the spec does not have, or a skill it does not pick, is `SPEC_INVALID`.
- `combination.parts` gains `subagents` and `skills`; no combination with either is `verified` yet.

The project is the starter's shape: `agent.yaml` (with `knowledge:`, `tools:` and `mcp:` entries), the prompt and the cases as `src/prompt/` and `src/evals/`, published as `prompt/NAME-prompt@0.1.0` and `eval/NAME-evals@0.1.0` into `DIR/registry`, the `--stack-for` stack (`chat` and `judge` aliases, 5 USD and 60 rpm; with `knowledge`, also the embedding alias in `environment.models` and the gateway config, and `service/postgres-pgvector@1.2.0` instead of the starter's `1.1.0`, whose `init.sh` creates the `vector` extension, so the runtime's `kb_<name>_<version>` table lands in the `app` database's `public` schema, where `knowledge status` reads it) with an `mcp:` entry per server named after its ref, each server's tools granted to the agent as `mcp grant` would (`environment.agents.NAME.mcp`), and `agent.lock`. The same destination rules, staging and rollback as the starter apply. `--json` prints the starter's summary plus, for each file, its full text in `content` (the console's preview shows this, never YAML of its own), `spec_version`, `combination` (`parts`, and `verified`: true only for a combination run end to end on its runtime (kept per runtime name since #1083 F1; only `runtime/adk` at the starter's version has runs), today: with `gemini`, model + prompt + evals alone or with one knowledge version, one tool, or one knowledge version and one tool (on `main`, not in a published preview, #833), with `openrouter`, model + prompt + evals alone (on `main`, not in a published preview, #1020; it has no embedding model, so no knowledge), and with `openai`, model + prompt + evals alone or with one knowledge version (on `main`, not in a published preview, #1020, embedding with `openai/text-embedding-3-small` at 1536 dimensions); two or more tools, any MCP server, and a tool with any provider other than `gemini` are unverified), `refs` (`{ref, kind, root_kind, runs_code, sha256}`, the version's content digest; a pinned runtime first, then knowledge, tools, MCP servers and skills), `aliases` (`chat`, `judge`, sub-agents' own aliases and, with knowledge, the embedding alias), `runs_code`, `grants` (`[{server, tools}]`), `knowledge` (`[{ref, alias, dimensions, embedding_model, top_k, extra_searches, documents, chunks}]`: the counts `knowledge status` expects the runtime to index; the index is built at the agent's first search), `keys` (the model key, sub-agents' model keys and each MCP server's imported keys) and `plan_sha256` (the digest of every file's text, the refs and the destination). The write also refuses (`DIGEST_MISMATCH`) a picked version whose content changed before `agent.lock` was written. `--expect-digest sha256:…` refuses the write with `DIGEST_MISMATCH` unless the plan is still the previewed one (the spec, a picked version or the date changed), `DIGEST_INVALID` if malformed. A dry run also loads the generated stack and reviews its gateway config, as the write does. Unverified combinations are written too; the text output says they have not been run end to end, and names code refs from outside the built-ins. A gemini spec with one knowledge version and no tools or MCP servers has been run end to end from a wheel built from `main` (`services up`, `build`, `release`, `invoke` answering from an article, `knowledge status` fresh; #833). So have a gemini spec with one path tool, alone and with one knowledge version (`release` through an eval case that requires the tool, `invoke` calling it; #833), and an openai spec with one knowledge version and no tools or MCP servers (#1020: indexed 4 of 4 chunks, `release` 2/2, `invoke` 2/2 answering from the articles). No combination with two or more tools or with MCP servers has.
