# `agentbreeder new`

Write a starter project (`new agent NAME`).

`new agent NAME --model gemini [--dir DIR] [--dry-run] [--json]` writes a starter project to `DIR` (default `./NAME`; it must not exist, or be an empty directory you own that others cannot write to, never a symlink): `agent.yaml` (`runtime/adk@1.0.6`, `traces: none`, `agent_events: none`, and a comment on the edit loop), `stack.yaml` (Postgres and LiteLLM, `chat` and `judge` aliases, a `DATABASE_URL` binding, `candidate: true`, `review_by` 180 days from today), `stack/litellm/config.yaml`, and the editable sources `src/prompt/` and `src/evals/` (the two eval cases run on 3.0.0a2, `retries: 1`); it publishes `prompt/NAME-prompt@0.1.0` and `eval/NAME-evals@0.1.0` into `DIR/registry` and writes `agent.lock`, so `build --locked` passes. Files are 0644 and directories 0755; on failure it removes what it wrote.

`--model` is required and only `gemini` is offered (the only provider run end to end). `--dry-run` writes nothing; `--json` prints the files (path, mode, hash) and the published refs, and on a refusal `{"schema_version": 1, "error": {"code", "message"}}` (exit 2; argparse usage errors stay plain text). A group-writable existing `DIR` is accepted only off macOS and only for your own group.

The template ran once end to end from a checkout on macOS (2026-11-12, `release` 2/2).

To change the prompt: edit `src/prompt/prompt.md`, bump `version:` in `src/prompt/manifest.yaml`, `registry publish src/prompt`, change the ref in `agent.yaml`, then `build` and `release`.

`new agent NAME --model gemini --stack-for DIR/agent.yaml [--dry-run] [--json]` onboards an existing `agent.yaml` alone: it writes only `stack.yaml` and `stack/litellm/config.yaml` beside it (neither may exist; nothing else in the project changes), the starter's stack with one gateway alias per model the agent uses (its `model.alias` and its eval set's `judge.alias`, which must resolve from the project's registry or the built-ins) and ceilings of at least the agent's own `budget_usd` and `rpm` (5 USD and 60 rpm otherwise), so the gate does not refuse its deploys. `NAME` must be the agent's `name`. An agent with `knowledge`, `tools` or `mcp` is refused (`STACK_FOR_UNSUPPORTED`: those need services this stack does not have; write `stack.yaml` by hand, see `services.md`), as is an alias other than letters, digits, `.`, `_` and `-` (`ALIAS_UNSUPPORTED`); `traces: otlp` gets a warning, since the stack has no trace collector. The directory and `agent.yaml` must be yours and not writable by others, and so must every ancestor (yours or root's; a sticky directory such as `/tmp` is allowed), the check console registration applies (`PROJECT_UNSAFE`). Files are staged, validated and hard-linked into place (an existing file is never replaced); on failure what it created is removed. `--json` prints `agent_file`, `aliases`, `files` (path, mode, hash) and `warnings`; refusals have the same error object. For the starter's own `agent.yaml` it writes the starter's stack (a test checks this); onboarding has not yet been run end to end with `services up` and `release` (on `main`, not in a published preview).

Flags: `agentbreeder new --help`.
