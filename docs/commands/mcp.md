# `agentbreeder mcp`

Grant or revoke an agent's MCP tools in stack.yaml.

Implemented, on `main` (not in a published preview) (#831, M15): `mcp grant|revoke AGENT SERVER TOOL… [--project DIR] [--dry-run | --expect-base SHA256] [--json]` edits one agent's grant in the project's `stack.yaml`, `environment.agents.AGENT.mcp.SERVER` (see [MCP servers through a relay](../services.md#mcp-servers-through-a-relay)). A stack has one `environment:` block, so the command takes no `--environment`.

- **What it checks.** AGENT must be an `environment.agents` entry (`MCP_AGENT_UNKNOWN`; the command never adds an agent, which needs a sponsor and `review_by`). SERVER must be an `mcp:` entry (`MCP_UNKNOWN`). A TOOL must be a valid tool name (`MCP_TOOL_INVALID`). `grant` refuses a tool the server's `mcp/<name>@X.Y.Z` version doesn't declare (`MCP_TOOL_UNDECLARED`, the same check `services up` makes). `revoke` takes any granted name, including one a newer version no longer declares.
- **What it writes.** It changes only that agent's `mcp:` value, rewritten in flow style (`mcp: {github: [get_me, list_issues]}`), or one added `mcp:` line. The rest of the file, comments included, is kept byte for byte. Comments inside the old `mcp:` value are dropped, and the diff shows that. Revoking a server's last tool drops the server from the grant. The rewritten file must parse to the old document with only that grant changed, and must still be a valid stack, or nothing is written (`STACK_EDIT_AMBIGUOUS`). A grant that would take the file over the 64 KiB limit every command reads is refused (`STACK_TOO_LARGE`). Line endings (LF or CRLF) are kept. The write is an atomic replace. Both verbs are idempotent: a grant already held, or a tool not granted, changes nothing (`changed: false`, no write).
- **Review first.** `--dry-run` prints the diff and the file's digest. `--expect-base SHA256` writes only if `stack.yaml` is still that digest (`BASE_MISMATCH`), as `agent set-ref` does. No audit row is written; the record is the file and git.
- **When it takes effect.** Nothing talks to a relay or a deployment. A grant reaches the relay at the next `services up`, and an agent uses a tool only when its `agent.yaml` asks for it (`mcp: [{ref, tools}]`); `deploy` refuses requested tools the stack doesn't grant (`MCP_TOOL_NOT_GRANTED`). A revoke is still written when an active deployment holds the tool, and is reported as `in_use` (read from the stack's grant files). `services up` refuses to narrow it (`MCP_GRANT_IN_USE`) until that deployment is removed, so the text output prints `Next: agentbreeder remove ID --local --stack DIR` and then `services up`. An unreadable grant file for the server also blocks `services up`; it is listed with `deployment: null` and a `Next:` naming `reconcile`.
- **Output.** `--json` prints `{schema_version: 1, file, verb, agent, server, ref, added|removed, tools: [{name, effect}], changed, base_sha256, sha256, diff, dry_run, in_use: [{deployment, environment, tools}]}`. A refusal exits 2 and prints `{schema_version: 1, error: {code, message}}` on stdout (with `--json`) and `[CODE] message` on stderr.

An example project is `tests/fixtures/mcp_github_project`: the `new agent` starter plus `mcp/github@1.0.0`, with the agent asking for the read-only `get_me` and `list_issues`. Grant, revoke and the in-use refusal are tested offline with Docker faked. A live run (a real deploy whose relay lists the granted tools) needs Docker and a `GITHUB_MCP_TOKEN` and has not run yet (M15 verification).

Flags: `agentbreeder mcp grant --help`.
