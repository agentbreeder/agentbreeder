# `agentbreeder services`

Local backing services from stack.yaml (local-only preview).

Local-only preview (#734): `services up|status|logs|env|down` (and, on `main`, `start|stop|restart`) start a project's `stack.yaml` backing services with Docker Compose and write a demo operator config under `~/.agentbreeder/stacks/` (see [`services.md`](../services.md)); `--stack DIR` on `build`, `deploy`, `eval`, `release`, `status`, `remove` and `reconcile` uses it.

`services up DIR --environment ENV [--locked | --update] [--env-file FILE] [--yes]` shows the grant and needs `--yes` when it is new or changed (`--update` accepts new hashes for edited project files such as an `init_sql`, never for a published service version); `services down [--volumes | --purge] --yes` deletes the stack's volumes, or with `--purge` everything `up` made (volumes, built service images, generated secrets, operator config and history). On `main`, not in a published preview (#1048): every `down` also removes the stack's networks Compose leaves behind (labelled with the stack's id and named after it, such as a dropped `mcp:` entry's `agentbreeder-<stack-id>-mcp-<name>`), also after a failed `up`; one still in use is kept. `--json` adds `networks_removed` and `networks_left`; the text output prints `Removed network NAME` and `Kept network NAME (still in use; …)`. Networks left by earlier versions are never pruned automatically; see [`services.md`](../services.md) for cleaning them up by hand.

Verified end to end with `src/agentbreeder/examples/northwind` (built-in `postgres-pgvector`, `litellm` and `phoenix`, two project services built from source, least-privilege database roles for the agent and the ops service; release 61/61, 2026-11-08 from a checkout and 2026-11-10 from PyPI `3.0.0a1`).

`services render [DIR] --cluster --environment ENV --out DIR [--image NAME=IMAGE@sha256:DIGEST ...] [--env-file FILE] [--json]` writes a Helm 3 chart for the stack's services (#772 K3; on `main`, not in a published preview; **never installed on a cluster**, and `helm lint`/`helm template` have not been run on its output). It needs no cluster and no `helm`. It reads the locked stack (`stack.lock` must exist and match, as `up --locked`; it is never written) and renders the same plan as the Compose file: per service a ServiceAccount, ConfigMaps for its `files/` and file params, a Deployment (a StatefulSet and headless Service when it has a volume) and a ClusterIP Service named after the service; `init` and `bootstrap` steps as Jobs under `jobs/`, outside the release. Secrets are referenced by name only (`ab-svc-…`; listed in `agentbreeder.lock`); before writing, the chart is scanned for every value the stack stores locally and every imported variable's value (`CHART_SECRET_LEAK`, naming the file, never the value). A service built from a Dockerfile needs `--image` with its pushed digest. `--out` must be new, empty or a previous render (replaced whole). `--json` prints `{"schema_version": 1, "stack", "environment", "chart", "version", "out", "tiers", "jobs", "secrets", "operator_only_secrets"}`. Errors (exit 2; the JSON error object under `--json`): `RENDER_TARGET` (no `--cluster`), `CHART_LOCK_MISSING`, `CHART_IMAGE_REQUIRED`, `CHART_IMAGE_INVALID`, `CHART_MCP_UNSUPPORTED` (stacks with `mcp:`), `CHART_HOST_UNSUPPORTED` (a gateway routed to the operator's host, Ollama), `CHART_USER_HOST`, `CHART_ROOT_USER`, `CHART_FILES_TOO_LARGE` (over 900 KiB in one ConfigMap), `CHART_FILES_INVALID`, `CHART_SECRET_LEAK`, `CHART_HARDENING`, `CHART_EXPOSURE_REFUSED`, `CHART_OUT_NOT_EMPTY`, `CHART_OUT_INVALID`, and the lock's own codes (`HASH_MISMATCH`, …). See [`services.md`](../services.md#a-helm-chart-for-a-cluster-preview-not-run).

`services logs` now uses the same redactor as [`logs ID`](logs.md) (literal, base64, URL-quoted and JSON-escaped forms, URL passwords) and also redacts the stack's deployments' secret copies (on `main`, not in a published preview).

`services logs [DIR] NAME [--tail N] [--since D] [--follow] [--json] [--raw]` reads a stack service with `docker compose logs --no-color --no-log-prefix --timestamps` (`--tail` default 200, at most 10 000; a 4 MiB cap), joins Docker's 16 KiB partial records, redacts every line and prints nothing when a value it needs cannot be read (`REDACTION_INCOMPLETE`, as `logs ID`); controls are shown as visible escapes unless `--raw`. `--json` prints `{"schema_version": 1, "source": "service", "target": "local", "name", "lines", "truncated"}`, the same shape as `logs ID`, and `--follow` streams with the same stop rules, NDJSON lines (`source`, `target`, `name`, `line`) and end record. Lines start with Docker's timestamp (no `name |` prefix). A follow carries on across the service's container restarts and stops compose and its plugin together. Errors are coded (`DOCKER_LOGS_FAILED` when compose cannot read the logs), with the JSON error object under `--json`; compose's own stderr is never shown (on `main`, not in a published preview).

`services logs` takes `--level warning|error` as `logs ID` does; see [`logs`](logs.md).

`services usage [DIR] [--follow] [--json]` shows one stack's resource use, reading only: its containers are matched as `watch` matches them (stack services by label, agent containers by this stack's deployment IDs) and listed again every 10 s, and one streaming `docker stats` child runs over exactly those container IDs (replaced when the set changes; no child at all when nothing is running).

`--json` prints one object per line, each with `schema_version` and `event`: `sample` (`time`, `containers` with `source`, `name`, `deployment`, `role` for a sidecar, `cpu_percent`, `memory_used`, `memory_limit`, `memory_percent`, `network_rx`, `network_tx`, `block_read`, `block_write` and `pids`; bytes as integers, null where Docker has no value), at most one every 2 s; `disk` (`as_of`, `stale`, `volumes` with `name` and `size`, `containers` with their writable-layer `size`) from `docker system df -v` every 60 s, read on a worker thread and cached, so `as_of` says how old it is and `stale` that the latest reading failed; and, when it is stopped, the end record `{"event": "end", "reason": "stdin|signal|interrupt", "dropped"}`. CPU and memory are of the Docker VM on Docker Desktop. Without `--follow` it prints one sample and one disk reading and exits (`DOCKER_STATS_FAILED` if they do not come within 30 s).

`--follow` stops, with its `docker stats` child, on the end of a non-terminal stdin, SIGTERM, SIGHUP or Ctrl-C (`docker stats` ignores SIGTERM, so it is killed). `docker stats` exits at once when a listed container is already gone, so a child that ends is replaced after a new listing; when three in a row end, or the containers cannot be listed three times in a row, it fails with `DOCKER_STATS_FAILED`. Docker's container names, labels and mounts are never printed; labels are not authenticated, so usage is best effort (on `main`, not in a published preview).

`services start|stop|restart [DIR] NAME [--json]` act on one existing service container with `docker compose start|stop|restart` (`restart` passes `--no-deps`; checked with Docker Compose 2.33.1, and an older Compose without that flag fails with `DOCKER_FAILED`): nothing is re-rendered, recreated or pulled, the grant is not shown and no other container is touched. `NAME` is a service in `stack.yaml` or an MCP relay. `stop` and `restart` refuse with `SERVICE_IN_USE`, naming the stack's active deployments (local and cluster), unless `--yes` is given; with `--yes` they print a `WARNING:` line naming them. `start` needs no `--yes`. The in-use check is advisory, not atomic: `deploy` and `remove` take no stack lock, so a deployment that starts between the check and the action is not seen. `--json` prints `{"schema_version": 1, "stack", "service", "action", "state", "health", "in_use"}`, read from `docker compose ps` after the action (`health` is often `starting` right after a start or restart; poll `services status`). A service with no container is `SERVICE_NOT_CREATED` (run `services up`), an unknown name is `SERVICE_UNKNOWN`, a host port another process holds is `PORT_BUSY` (`start` and `restart`) and any other Docker failure is `DOCKER_FAILED`. Errors print a `[CODE] message` line on stderr and, under `--json`, `{"schema_version": 1, "error": {"code", "message"}}` on stdout, as `services logs` does. Exit 0 on success and 2 on any error (on `main`, not in a published preview).

Every `services` write (`up`, `down`, `start`, `stop`, `restart`, `plan`, which records host ports and file copies, `pins`, `render`, and `cluster up|down` on the stack) holds a per-stack lock, taken before the stack's state is opened, `~/.agentbreeder/stacks/.locks/<stack-id>.lock` (it follows `AGENTBREEDER_STACKS_DIR`; a 0600 file, never deleted, outside the state directory so `down --purge` cannot remove it while held). A second write on the same stack fails at once with `[SERVICES_BUSY] another services operation is running on this stack; retry when it finishes` (exit 2; under `--json` also the error object). It is held for the whole command, including while `up` waits at an interactive grant or pin prompt. Reads (`status`, `logs`, `usage`, `env`) take no lock. `cluster up|down` take the machine-wide cluster lock first, then the stack lock (on `main`, not in a published preview).

Codes for the console (lane B): `SERVICES_BUSY` (another write holds the stack; retry later), `SERVICE_IN_USE` (stop or restart while deployments use the stack; confirm, then pass `--yes`), `SERVICE_NOT_CREATED`, `SERVICE_UNKNOWN`, `DOCKER_FAILED`, `PORT_BUSY` (`up`, `start` or `restart` could not bind a host port because another process or container holds it: `port N is already in use on this machine (STEP); stop what uses it, then run the command again`, with only the port number taken from Docker's output; a stack keeps the host ports it recorded at its first `up`, and only `down --purge` forgets them), `STATE_UNSAFE` (the lock file or directory is not private), `STACK_CHANGED` (`stack.yaml`'s name changed while the command started; run it again), `SERVICE_UNHEALTHY` (`up`: a service's HTTP health check did not pass within 180 s, or within 240 s more while its container was still running; a container that exited fails at 180 s; started services are kept, so `up` can be run again with the same flags) and `STATE_UNREADABLE`. Because `plan` is a write, a grant preview (`services plan`) that overlaps a running `up`, `down`, `start`, `stop` or `restart` on the same stack fails with `SERVICES_BUSY` until that write ends. Under `--json`, `up`, `plan`, `status` and `down` also print `{"schema_version": 1, "error": {"code", "message"}}` on stdout for every coded error, including `SERVICES_BUSY`, `STACK_MISSING`, `CONFIRM_REQUIRED` (`down --volumes` or `--purge` without `--yes`) and `STATE_UNREADABLE`, beside the `[CODE] message` line on stderr; without `--json` stdout stays empty. Exit 2 (on `main`, not in a published preview).

`services pins [DIR] [--json]` is the review for an MCP repin without a terminal (#964). It probes every relay of the stack inside its container (admin token on stdin, never minted: a missing one is `MCP_ADMIN_TOKEN_MISSING`) and builds one review document per stack: for each `mcp:` entry its identity (version ref, origin, upstream origin, token host), its current pins, the tools a repin would `accept` (new and changed, each the hash of the whole live definition) and the pins it would `drop` (pinned tools missing upstream). The review digest is the sha256 of that document's canonical JSON. Human output shows each accepted definition in full (ASCII-escaped sorted JSON; display lines longer than 100 columns are wrapped with a `↩` marker, which never changes the digest), a unified diff against the pinned definition when the relay's pins file still holds it ("previous definition unavailable" otherwise; "diff too large" past 2,000 lines), the dropped pins ("this pin is removed") and declared tools missing upstream that were never pinned ("not pinned", not bound), then `Review digest: <hex>` and the `up` command that applies it. `--json` prints `{"schema_version": 1, "stack", "digest", "review", "servers"}`: `review` is the document exactly as hashed, and `servers.<name>` holds `origin`, `state` (`drift` when a pinned tool changed or is missing upstream, else `ok`), `new` and `changed` (`sha256`, `definition`; `changed` also `pinned` and `previous`, `null` when unavailable), `missing`, `drop` and `same`. A stack with no `mcp:` entries prints `servers: {}`. It never changes `stack.lock`, a pins file, a secret, the admin token, the ports table or a container, but it holds the stack's write lock (it may copy content-addressed files into the state dir, as `plan` does), for up to 180 s per relay. Errors: `MCP_RELAY_NOT_RUNNING` (run `services up` first), `MCP_PINS_NEED_UP` (a server has no pins but tools to pin: first pins, or a changed version, origin or upstream; run `services up` without `--repin`), `MCP_PROBE_FAILED` (no digest; any failing relay fails the whole read), `SERVICES_BUSY` (on `main`, not in a published preview).

`services up DIR --environment ENV --repin --expect-pins SHA256` repins without a TTY. Before anything runs, `--expect-pins` must be 64 lowercase hex characters (`PINS_EXPECT_INVALID`) and needs `--repin` without `--locked` (`PINS_EXPECT_NEEDS_REPIN`). The grant step is unchanged (`--yes` or `--expect-grant`, and `--allow-project-mcp`). After the relays start, `up` probes every relay, rebuilds the review and compares its digest. On a match it applies every server's `accept` and `drop` with the hashes from those probes, saves `stack.lock` once, then rewrites every relay's pins file; nothing to change is a success with no lock write. On any difference it pins nothing, leaves `stack.lock` and the pins files as they were and fails with `PINS_CHANGED`; the rest of `up` has already run (grant recorded, services and relays started), and the operator config is not rewritten. `MCP_PINS_NEED_UP` refuses a repin while any server still needs first pins. `--json` adds `"repinned": {"<server>": {"accept": [...], "drop": [...]}}` (servers with a change only) and `"pins_digest"` at the top level of the result; human output prints a `repinned:` line per server and `Pins digest: <hex>`. The prompt is never shown. Without `--expect-pins`, `--repin` still asks at a terminal, and `--yes` never accepts a changed definition (`MCP_PINS_NOT_CONFIRMED`). The digest is content-bound, with no expiry: it proves the definitions were fetched and are unchanged, not that a person read them (on `main`, not in a published preview).

A relay's failed upstream check names its cause (#1042). When a relay's probe fails with one of its own codes (`UPSTREAM_AUTH`, `UPSTREAM_TIMEOUT`, `UPSTREAM_ERROR`, `UPSTREAM_INVALID`, `UPSTREAM_PROTOCOL_UNSUPPORTED`), `MCP_PROBE_FAILED`'s message names it in parentheses, and `services status --json` (and `up`'s `mcp` result for a server pinned before) report `mcp.<server>` as `{"state": "unverified", "error": "MCP_PROBE_FAILED", "cause": "UPSTREAM_AUTH"}`; `cause` is left out when the relay gave no plain code. A confirmed `up` (after the grant was accepted) that fails with a coded error records that code and cause, never the message, in the stack's `stack.db` for the environment; a later successful `up` clears it. `next` reads it to say the last `up` failed (`SERVICES_UP_FAILED`, see [`next.md`](../next.md)) instead of "has not run" (on `main`, not in a published preview).

Flags: `agentbreeder services --help`.
