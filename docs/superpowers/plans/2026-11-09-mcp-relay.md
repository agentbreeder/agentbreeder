# MCP relay (#745, slice 4b of #734): implementation plan

Spec: `docs/superpowers/specs/2026-11-08-agent-services-design.md` §7 (§7.4, §7.6 and §7.7 are
normative; r6/r7 review notes). Slice 4a (#744) shipped the contracts: the `mcp` kind, grant
files, deploy checks and the grant lifecycle. This slice adds the relay itself and makes
`services up` run it.

## Decisions taken while planning

1. **The relay is stdlib-only Python** inside the built-in version
   `service/mcp-relay@1.0.0` (`relay/relay.py`, built by its own Dockerfile from the pinned
   `python:3.12-slim` digest the sidecar uses). It vendors the pieces it needs from
   `egress/protocol.py` and `egress/sidecar.py` (JSON-RPC parsing, `resolve_destination`,
   `_PinnedHTTPS`), because a registry version is self-contained and hash-locked.
2. **It resolves only from the built-in root.** `lock_stack` materialises it with
   `search=[BUILTIN_ROOT]`, and `stack.yaml` can't name `service/mcp-relay` (`RELAY_RESERVED`).
3. **One relay container per `mcp:` entry**, named `mcp-<server>` (`_` becomes `-`). It is a
   synthetic stack service: the engine derives its spec from the relay's `service.yaml`
   (egress only for remote upstreams; the mcp version's secrets plus a generated admin token).
   A name clash with a stack service is refused.
4. **Configuration** is a generated JSON file mounted at `/run/params/config`: server name,
   upstream (URL, or the service address on the private network), auth type and header name,
   `token_url`, scopes, declared tools, the per-agent configured grant, allowed ports (443) and
   the admin token's hash. No secret values.
5. **Credentials** are 0400 files in a per-generation mount at `/run/secrets`. The relay runs
   as the operator's uid (`user: host`), so a 0400 file is readable by it and nobody else. This
   is the "fixed uid" of §7.6.10 on a single-user local stack.
6. **Grants:** the stack's `grants/` root is bind-mounted read-only at `/run/grants`. For a
   token the relay looks only at `/run/grants/<env>/<its server>/<sha256>.json`, re-read per
   request; the file's `server` and `environment` must match its location.
7. **Pins** live in `~/.agentbreeder/stacks/<id>/pins/<server>/pins.json` (0444, directory
   0755), mounted read-only at `/run/pins` and re-read when its mtime changes, so re-pinning
   doesn't recreate the relay. `stack.lock` gains an `mcp` section: per server the ref, origin,
   upstream origin, `token_url` host and tool hashes.
8. **Probe (phase 2)** runs inside the relay. The engine runs `docker compose exec -T` with the
   admin token on stdin (never in argv, env or labels). The relay's admin listener is bound to
   127.0.0.1 inside its container and checks the token's hash. The probe initializes upstream,
   follows `nextCursor` up to 20 pages, closes the session, and returns each declared tool's
   canonical definition and hash, plus the declared tools that are missing upstream.
9. **Live checks:** the relay checks live definitions against pins on each `tools/list` and,
   for `tools/call`, when the session's last check is older than 5 minutes. A tool whose live
   hash differs is hidden and refused (`TOOL_DEFINITION_CHANGED`). A tool missing upstream is
   hidden and reported separately (`TOOL_MISSING_UPSTREAM`).
10. **`services status`** runs the probe on each running relay and reports `changed` and
    `missing` per server against `stack.lock`.
11. **Service upstreams** must be a stack service with that ref whose port is
    `expose: internal`, which no other service wires to and no binding or agent URL names. It
    joins only a private internal network `<project>-mcp-<server>` shared with its relay (and
    `edge` if it declares egress). Its health probe runs on that network.
12. **Narrowing:** `up` reads the grant files under `grants/<env>/` (reconcile keeps only those
    of active deployments). A file whose server is gone, or whose tools aren't all still granted
    to its agent, refuses `up` (`MCP_GRANT_IN_USE`).

## Tasks (test first)

1. Relay core (`relay.py`): grant lookup and token shape, method allowlist, session map, the
   server-to-client filter, `initialize` rewrite, `tools/list` from pins, `tools/call` gating,
   concurrency, the 120 s and 1 MiB caps, logs, upstream auth (`bearer`, `header`,
   `oauth_refresh` with the rotation refusal), SSRF pinning, the probe and admin listener.
   Tests: `tests/test_mcp_relay.py` with a mock upstream (JSON and SSE) that counts calls.
2. Built-in version: `service.yaml`, `manifest.yaml`, `Dockerfile` (strict subset).
3. Lock: `mcp` refs and the relay version in `stack.lock`, origins, upstream origin and pins.
4. Plan and engine: synthetic relay services, private networks, the grant (origin, credential
   destination, per-agent tools with effect and hash), `--allow-project-mcp`, `mcp_relays` and
   agent grants in the operator config, grants dirs, the narrowing refusal, two-phase pinning
   (`--repin`, `--locked`), status. Remove `MCP_RELAY_UNAVAILABLE`.
5. CLI flags `--repin` and `--allow-project-mcp NAME`.
6. Opt-in real-Docker test: a stack whose relay fronts a mock MCP service upstream, an agent-side
   client on the agents network, restart → 404 → initialize again.
7. Docs: `docs/services.md` MCP section with the §7.6.13 claims; spec r8 notes.

Live built-in checks are #748 (owner credentials). The ADK client is #746.
