x86_64, Docker Desktop engine 27.5.1, kind 0.33.0). Every acceptance check passed except one, which is

## What changed (#851)

- `launcher.py`: printed commands use the form the user launched with: bare `agentbreeder`,
  `npx agentbreeder@<ver>` (from `AGENTBREEDER_LAUNCHER`/`AGENTBREEDER_LAUNCHER_VERSION`, which
  `npm/bin/agentbreeder.js` sets), `uvx --from …` or `python -m agentbreeder`. Every `Next:` line
  goes through one helper. `build` points at `release`, and `services up` prints absolute paths.
- Messages that name their fix: a `--stack` hint on `CONTEXT_ENVIRONMENT_UNKNOWN` and
  `MODEL_ACCESS_UNCONFIGURED` (G-F1, G-F2), `REF_UNPINNED` → `registry publish` (G-F4),
  `LOCK_STALE` → `build` (G-F5), failed cases on a failed gate (G-F6), and the demo-identity note
  only when the stack's generated config was selected (G-F9).
- G-F3 release evidence: "already in production" needs a `release/promoted` audit row. Otherwise
  `release` warns, evaluates the same image, records it on a pass, and exits 5 with working advice
  on a fail.
- Read-only `list`, the new `migrate`, `Docker.logs`, `redaction.py`, the saved failed-candidate
  tail and `logs --failed NAME`, the `doctor` PATH advisory (G-F10, #805), the S-11 cluster lock
  and S-08 escapes.

### Failed-candidate tail

. --environment dev` worked exactly as printed (exit 0), and `--json` gave `{"agent": "hello",

## Leak scan

The scan ran after teardown, over every file in the sandbox `HOME`, `TMPDIR`, all captured stdout
and stderr (`out/`, including saved Docker log tails and the `script` typescripts) and the project
directories (`work/`): 795 files. It compared against the actual `GEMINI_API_KEY` value in memory,
never printing it, and checked `AIza[0-9A-Za-z_-]{30,}` and `sk-[A-Za-z0-9]{20,}`. Result: **0 files**.

An earlier pass found `sk-…` in 3 files. All 3 were the verification script's own `cp -Rp`
copies of the hello state for the migrate checks. Each held that deployment's generated LiteLLM gateway key (a 0444 secret copy),
which stopped working when the gateway and its database were purged. The copies were deleted and
the scan rerun. No AgentBreeder output, log or state left in `HOME` contained a key. The secrets
file, the venvs and the wheel were not scanned. `services up` stores a copy of the Gemini key under
the stack's state, as documented. `services down --purge` deleted it, and that state was gone before
the scan ran. The real home path was not scanned for; the sandbox path and the script's Docker
context contain it.
