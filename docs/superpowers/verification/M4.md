## Findings

1. **`release` prints no `Next:` line.** After a successful release, the user must run `next`
   again (printed earlier by `new agent`) to be shown `Done. Try it: agentbreeder invoke …`. The
   guided spec does not require a line here, so this is not an acceptance failure; a small
   follow-up is to end a successful `release` with `Next: … invoke NAME Hello --stack … --environment
   …`.
2. **`next` exits 1 while steps remain** (step 3), by design (`docs/commands.md`). A script that
   follows `Next:` lines must not stop on it.

### APPROVAL_PENDING: not run

A local release needs a second person's approval only through a `require_approval` obligation,
from a PDP policy or from `maker_checker` (which itself needs a PDP). To try it, the generated
`operator.yaml` of the sandbox stack had a `pdp:` block added for a Cedar baseline permitting
`deploy` and `RequireApproval`. That file was backed up first and restored afterwards. Production
was removed and **Run release** was pressed. The job failed in 0.8 s, before any approval:
`[DEPLOYER_UNVERIFIED] A verified deployer identity is required (agentbreeder login); production
unchanged`. With a PDP configured, the gate needs a verified deployer (`agentbreeder login`
against an OIDC issuer), and the sandbox has none. So a pending approval cannot be created on
one machine without an identity provider. The console's handling of it was not seen live. What it
showed instead:

- The job row read "The release failed. See its log." The log held the coded line above.
- The checklist stayed on "Release (eval gate): No production deployment" (NOT_RELEASED), matching
  `next --json`.

The script then stopped on a selector error of its own (a locator that matched three checklist
items), after these checks. Nothing else was run.

Covered offline instead, on code matching `main` for these files (5 pytest passed, 10 node tests
passed):
- `tests/test_next.py`: release and kubernetes APPROVAL_PENDING are `blocked`, with no command.
- `tests/test_center.py`: an exit 3 job is `waiting_approval`.
- `tests/js/format.test.mjs`: `jobOutcome` for `waiting_approval` is a warning ("…waiting for a
  second person's approval… it cannot be approved here, because this session is one person").
- `tests/test_guide_contract.py`: kubernetes APPROVAL_PENDING is blocked.

### Findings

1. **The APPROVAL_PENDING path can't be reached locally.** A PDP makes the gate require a
   verified deployer before it evaluates any obligation, so the console's `waiting_approval`
   row and the APPROVAL_PENDING checklist step have only unit-test evidence. Live evidence needs
   an OIDC deployer (and a second verified person to approve).
2. **A coded release failure shows as a generic row.** `DEPLOYER_UNVERIFIED` showed in the job
   row as "The release failed. See its log."; the code is only in the log.
3. **After production was removed, the optional Kubernetes step said PROMOTION_STALE** ("The
   cluster runs an older release than production"), though there was no production deployment.
