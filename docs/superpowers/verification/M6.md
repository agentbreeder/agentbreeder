# M6 verification: Home and usage (#822)

Status: **partial: verified from `main` with Northwind on real Docker, except the Docker-stop step,
which was not run** (d123d4f, 2026-11-14 local time (2026-11-15 UTC), macOS 13.7.8 x86_64,
Docker Desktop engine 27.5.1). The console half was driven by Playwright against the real stack
and recorded as screenshots and saved page text, not video. The results:
- **Home shows each of Northwind's 5 services with CPU, memory, network and block IO updating
  within 10 s.** Home's Services table listed postgres, litellm, phoenix, proxy and ops. All four
  figures showed for all five rows 4.6 s after Home opened. By 8.3 s every row had changed:
  the network and block IO rates went from "no value" to a measured rate, and CPU changed on 4 of
  the 5 (proxy, idle, stayed at 0.0%).
- **`services restart litellm` restarts only that container.** Only litellm's start time changed;
  its container ID stayed the same (restarted, not recreated). The other four kept their IDs
  and start times. The console's **Restart** button on the litellm page did the same.
- **Stopping Docker shows the blocker within 15 s, and starting it clears it without a reload: not
  run.** Docker Desktop is shared with other sessions, so it was not stopped. The UI tests that
  cover it against the fake CLI were run on this commit instead (below). They are not the
  acceptance run.
- The leak scan found 0 hits. Teardown left nothing of this run (details below).

This is on `main`, not in a published preview.

- **Source:** `main` at d123d4f, exported with `git archive`, so no working-tree files.

  (5 s): `agentbreeder-3.0.0a2-py3-none-any.whl`, sha256

  `TMPDIR` inside it and `PIP_NO_CACHE_DIR=1`, in a fresh Python 3.12 venv holding only the wheel

## The Docker-stop step (not run) and the UI tests

The acceptance step "stopping Docker shows the blocker within 15 s and starting it again clears it
without a reload" was **not run**. Stopping Docker Desktop would stop the containers of the other
sessions that share this engine, and no window was arranged.

Instead, the console's UI tests for the blocker, the service controls and usage were run on this
commit, from the same export, with `AGENTBREEDER_UI_TEST=1` and system Chrome
(`--browser-channel chrome`): `tests/ui/test_docker.py` (6), `tests/ui/test_service.py` (9) and
`tests/ui/test_usage.py` (11): **26 passed** in 132.8 s. In
`test_the_blocker_shows_on_any_screen_and_clears_without_a_reload`, the fake CLI's `doctor` turns
Docker down. The blocker must show within 15 s ("Docker is not reachable.", doctor's message,
`agentbreeder doctor`). The fake's Docker then comes back, and the blocker must clear within
15 s, on the same document (no reload) and the same route. These tests use a fake CLI and never
stop Docker, so they cover the console's side only, not a real engine going away.

## Leak scan and teardown

**Leak scan.** Before teardown, while the stack's secrets still existed, a stdlib script searched
60 files:
- every saved output, including the console's `up` output, the Playwright logs and the Home
  samples;
- the console's state directory;
- the logs of the stack's 5 containers.

It looked for the literal, base64 and URL-quoted forms of:
- every `~/.env` value of 12 or more characters (6 values);
- every stored secret of 12 or more characters in the 25 files under the sandbox's
  `~/.agentbreeder` `secrets` paths.

It also looked for `/Users/`. Result: **0 hits**. The counts were printed to a saved file.

**Teardown:**
1. The console was stopped (it said "Console stopped. Services and deployments keep running").
2. `services down <P> --purge --yes` (exit 0, 14.2 s) stopped the stack, removed its volume, the
   two images it built (ops and proxy) and the stack state.
3. The key file was deleted.

After teardown, the container, volume, image and network lists matched the snapshot taken
before the run exactly (0 lines of difference each). The images the stack pulled were already
present.

## Findings

1. **The rates need two samples.** For the first reading, Home shows the network and block IO rates
   as "no value" and the totals since start. The rates appeared one sample later (8.3 s here,
   still within the 10 s). This is how `docs/command-center.md` describes them ("averaged between
   two samples"), so it is not a defect.
2. A new console takes longer for its first figures (6.5 s in part B, 4.6 s in part A), because
   it starts a new usage child. Both are within 10 s.
3. Not run, to do when a Docker window is arranged: the real Docker-stop step, and a GIF.
