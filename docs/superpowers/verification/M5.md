## Findings

1. **The agent writes no log lines.** `runtime/adk@1.0.6` printed nothing during 61 evals and an `invoke`, so `logs ID` for both deployments returned an empty, well-formed result (`lines: []`, `format: adk`). Reading, target selection and ownership checks were exercised; redaction of the agent's own lines was not (`M3.md` found the same). Redaction of real container output is covered by the opt-in Docker test above. A follow-up for the runtime (a startup line and one line per request) would make agent logs useful.
2. **Attempt 1 failed (a full disk plus driver bugs).** The first run (from `main` e373754, the same night) failed at `cluster up` with `postgres.init exited with status 1`; a second `cluster up` and a plain `services up` failed the same way (saved outputs). The cause, observed live and not in the saved outputs: the Docker Desktop VM disk was full (`df` inside a container: 56.1 of 58.4 GB used, 0 available) and postgres logged "could not extend file … No space left on device". With the owner's approval only the build cache was pruned (`docker builder prune -f`, 5.6 GB), and the rerun above passed. Three driver bugs also broke steps of that attempt: `--tail 0` is refused (the minimum is 1), so the follow printed nothing; `list --json` was captured with its stderr note, so the local `logs ID` failed (`ID_INVALID`), the scripted removes found no IDs to remove, and the scripted `services down` and purge then failed with `STACK_IN_USE` (the stack and the partly created kind cluster were torn down by hand afterwards); `cluster down` takes no `--environment`. The rest matched the rerun: release 61/61, no event for the release, `died` and `restarted` for postgres, and every service's logs read.
3. **One kind cluster per machine.** `cluster.py` uses a fixed cluster name and registry port, so two sandboxes on one machine share the cluster, and either `cluster down` removes it under the other. Lane B's M0b close-out ran at the same time; the two lanes took turns (`cluster up` to `cluster down`). Worth a line in the cluster docs, or a per-stack cluster name later.
