# M11 verification: stored events and `agentbreeder events`, CLI half (#827)

Status: **CLI acceptance verified from `main`** (12ec369, after #888 merged as 0fd540d, 2026-11-13,
macOS 13.7.8 x86_64, Docker Desktop engine 27.5.1) with Northwind (release 61/61). The results:
- A clean release, a `remove`, `services down` and `services up` stored **0 events**.
- `docker stop` and `docker kill` stored nothing.
- Postgres exiting by itself stored **exactly 1** `container_died` event, and no `restarted`.
- A release failing its eval gate (exit 5) stored **1** `gate_failed` event with its case ids
  and counts.
- `SERVICES_UNHEALTHY` showed while postgres was down and cleared after `services up`.
- `--mark-read` and `--mark-all-read` worked. The store stayed 0600 in a 0700 directory.
- The leak scan found 0 hits, and nothing of the stack was left running.

One caveat: with the stack's restart policy (`unless-stopped`), Docker restarted postgres within
the same second, so the condition could not be seen. The condition was checked in a second trial
with the restart policy turned off on that one container (see "Self-exit").

The **console half is open**: lane B wires `events.job_failed` and `watch --record` into the
console, so `job_failed` was not exercised. The Chrome click-through is open too.

This is on `main`, not in a published preview.

## Self-exit

**Setup mistake (not a result).** At 22:05:04, `docker exec <pg> kill -INT 1` failed with exit
126: the image has no `kill` binary. Nothing happened, and 12 polls over 22 s showed 0 events (seen in the terminal; those poll files
were overwritten by trial 1's).
The shell builtin was used instead.

**Trial 1, the stack as configured (restart policy `unless-stopped`).** At 22:05:35,
`docker exec <pg> sh -c 'kill -INT 1'` ran (exit 0). Postgres shut down by itself with exit 0, and
Docker restarted it at once (`RestartCount` 1).
- `watch` printed `died` (postgres, exit 0, no OOM) and `restarted`, both at 22:05:35.
- `events --project <project> --json` was polled 15 times from 22:05:36 to 22:06:04. Every poll
  showed **1 event** and `"conditions": []`.
- Postgres was already running again at the first poll, so `SERVICES_UNHEALTHY` could not be
  seen.

The stored event:

```json
{
  "id": 1,
  "time": "2026-11-13T22:05:35Z",
  "project": "<project>",
  "kind": "container_died",
  "source": "service",
  "name": "postgres",
  "deployment": null,
  "exit_code": 0,
  "code": null,
  "data": {"oom": false},
  "read": false,
  "message": "service postgres exited (exit 0)"
}
```

**Trial 2, restart policy off (a test-setup change on this one container).** This trial shows the
condition while postgres is down and its clearing after `services up`.

1. `docker update --restart=no <pg>`.
2. At 22:06:17, `docker exec <pg> sh -c 'kill -INT 1'` (exit 0). Postgres exited with exit 0 and
   stayed exited.
3. `events --project <project> --json` (exit 0) showed **one new event**: id 2, `container_died`,
   postgres, exit 0, `{"oom": false}`. It showed `"unread": 2` and `"conditions":
   [{"code": "SERVICES_UNHEALTHY", "message": "postgres is exited (none)"}]`.
   The text form (exit 0) printed:

   ```
   Needs attention:
   ! postgres is exited (none)
   Recent events (2 unread):
   *     2 2026-11-13T22:06:18Z service postgres exited (exit 0)
   *     1 2026-11-13T22:05:35Z service postgres exited (exit 0)
   ```

4. `services up <project> --environment dev --env-file <keys> --yes` exited 0, and postgres was
   `healthy`. `watch` printed `restarted` at 22:06:32.
5. `events --project <project> --json` (exit 0): `"conditions": []`, still the 2 events (ids 2
   and 1, both `container_died`). **No `restarted` event was stored.**
6. `docker update --restart=unless-stopped <pg>` restored the policy.

## Findings

1. **`--mark-read` with an unknown id is silent.** `events --mark-read 999` exits 0 and lists the
   events as usual; nothing says the id was not found. `docs/events.md` does not say what should
   happen. This is not an acceptance failure, but the docs could say so, or the CLI could warn.
2. **A restarted container hides the condition.** With the restart policy the stack uses,
   postgres was back within the same second in this run. The stored `container_died` event was
   then the only trace; a poll can see `SERVICES_UNHEALTHY` only while the service is down, which
   a slow or failed restart would make longer (not tested).
   That matches `docs/events.md` ("the condition clearing already shows the recovery").
3. **The postgres image has no `kill` binary.** `docker exec <pg> kill -INT 1` fails with exit
   126. Use `sh -c 'kill -INT 1'`. M5 used `kill -INT 1`; whether its image differed was not
   checked.
