### Hashes

`registry verify` prints no per-version hash (`--json` lists only problems, and gave `[]`). So each
`show --json` sha256 was compared against two other sources:

- **The lock files:** `agent.lock` covers 9 refs (including `runtime/adk@1.0.6`) and `stack.lock`
  covers 5 (`service/litellm`, `phoenix`, `postgres-pgvector@1.1.0`, `northwind-ops`,
  `northwind-proxy`). 14/14 match. The two lock entries that are not registry refs
  (`path:stack/db/commerce.sql`, `path:stack/litellm/config.yaml`) are rightly not listed.
- **An independent re-publish:** each version directory was copied into a scratch project and run
  through `registry publish --to <scratch>/registry --json`, which hashes along the publish path.
  27/27 match, including the 13 refs that have no lock entry (e.g. `prompt/northwind-support@1.0.0`
  `sha256:2b41e429…`, `eval/northwind-golden@1.0.0` `sha256:d4b92fc6…`, every unused built-in).

The per-file sha256 values in `diff --json` (`manifest.yaml` `6bb7ae6f…` → `0653e9bd…`,
`prompt.md` `6411d899…` → `2b9b480e…`) also equal `shasum -a 256` of the files.

### Diff

`registry diff … --context C` was compared with `diff -U C -r 1.0.0 1.0.1`, run inside
`registry/prompt/northwind-support/`. After dropping the `diff`, `---` and `+++` header lines, the
hunks were byte-identical (`cmp`) for C = 3, 0 and 10, and for 1.0.1 → 1.0.0 at C = 3.

- Hunks at context 3: `manifest.yaml @@ -1,4 +1,4 @@` and `prompt.md @@ -4,11 +4,11 @@`.
- Hunks at context 0: `@@ -3 +3 @@`, `@@ -7 +7 @@` and `@@ -11 +11 @@`.
- The only differences are the headers. `registry diff` labels sides
  `--- prompt/northwind-support@1.0.0/prompt.md`, with no timestamp and no `diff …` command line,
  while `diff -u` prints `--- 1.0.0/prompt.md<TAB><mtime>`. No change here adds or removes a whole
  side, so the documented context-0 numbering difference for an empty side did not arise.

## Findings (not M8 acceptance failures)

For a service ref (`registry used-by service/litellm@1.0.0`), it showed `declared stack.yaml at
services.litellm.ref` and `locked stack.lock … (builtin)`. The running agent appeared under
`undetermined` with the reason "the build record for its image does not list this ref". That
matches `docs/registry.md`: a service ref is never "deployed", and "the record does not list the
ref" is a documented `deployed_undetermined` reason. It reads oddly for a service ref, though, and
could be omitted for service kinds. This is a note, not a failure. Follow-up issue: #854.
