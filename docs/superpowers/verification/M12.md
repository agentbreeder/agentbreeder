built-in tool fork were not run, and two known blockers remain** (f0606ef, 2026-11-14,

- Northwind's project-owned `tool/orders` was edited to `1.0.1`, and the agent was moved to it
  with `agent set-ref`. The release then passed **61/61** and went to production. Northwind was
  relocked on `service/postgres-pgvector@1.2.0` and `runtime/adk@1.2.0`.

  through the console credential, with no arguments unless `--content` was given.

  signatures from `ast`, also for a module whose top level raises.
- The leak scan found 0 hits. Teardown left no container or volume of this run.

Two known blockers:
- **Release (#978):** 3 of 4 `release` attempts failed with "Container is not running with one
  loopback HTTP binding". That is a race in the deploy path. One attempt passed 61/61 on the
  candidate and then failed its production deploy.
- **`services up` (#979):** the first `services up` failed with `SERVICE_UNHEALTHY` for LiteLLM,
  because its 180 s probe ran out. The re-run passed.

The **console half was not run here**: tool detail, the code editor with the three-tier confirm,
and the execution log tab (#955, #961, #963). Their Playwright specs run in CI. There was no

**What the `docker inspect` loop saw (#978).** A loop ran during attempts 2 to 4: every 0.5 s in
attempt 2, every 0.3 s in attempts 3 and 4. Each agent container it caught after `start` was
first `running` with `"Ports": {"8080/tcp": []}`. The loopback binding appeared on the next
sample. `deployment.py` inspects once after `start` and calls `endpoint()`, which needs exactly
one binding.

  the attempt 3 candidate.

## Findings

1. **#978: the deploy reads the port binding once.** On this Docker Desktop, a started container
   can show `"8080/tcp": []` for a moment after `container start`. `deployment.py` inspects once
   and fails with "Container is not running with one loopback HTTP binding". It failed 3 of 6
   container starts in this run (2 candidates and 1 production deploy). Attempt 1 had no
   inspect loop; its message was the same. Fix: a bounded re-inspect
   before `endpoint()`, in its own PR (it touches the deploy path).
2. **#979: the LiteLLM probe can expire on a fresh stack.** LiteLLM's container started at
   01:03:41Z and printed its first line at 01:06:39Z, 178 s later, with no restart. The probe
   waits 180 s. The engine was busy: the #944 Docker tests ended at about 01:03:35Z. A re-run of
   `services up` completed the stack.
3. `services logs` takes the project as a positional `DIR` (`services logs <project> litellm`),
   not `--project`. A first try with `--project` was a usage error (exit 2) on my side, not a
   product finding.
