## 1. Problem

The plan's M19 asks for "two agents call each other through governed A2A, with grants and audit
rows". Today nothing lets one AgentBreeder agent call another:

- `agent.yaml` has no field that names another agent; M13 adds the `agent` registry kind and the
  package `agent/<name>@X.Y.Z` but explicitly leaves a reference field to M19 (M13 §3, §9).
- An agent's `/invoke` is unauthenticated and its customer is free text (#780 §1). An agent that
  could reach another on the agents network could already call it, as any container can, and name
  any customer. #780 fixes that for `runtime/adk@1.2.0` and forbids handing one agent another's
  key (#780 T12, §9).
- The only governed outbound path is the MCP relay: a per-deployment token, a grant from the
  operator config, the relay's JSON log lines. It speaks MCP only, does not learn the customer
  (#780 §8.3, D5) and does not write the host audit chain.
- The opt-in `mcp_http` sidecar cannot be used: `runtime/adk` cannot run under it
  (`deployment.py` `MCP_RELAY_UNSUPPORTED`, `MODEL_ACCESS_UNSUPPORTED`), and Kubernetes refuses
  `mcp_access` (`KUBERNETES_MCP_UNSUPPORTED`). So A2A governance cannot be sidecar enforcement.

## 2. Goal

- An agent built on the new runtime version (`runtime/adk@1.3.0`) can call another such agent by
  its released package, `agent/<name>@X.Y.Z`, with the A2A 1.0 `SendMessage` operation. Pinned
  references form an **acyclic** graph at build time (§8.2): A@1 can call B@1, and a later B@2 can
  call A@1, but no two pinned versions can call each other.
- Every call goes through a **host-side broker**. The caller never holds the callee's key or a
  token for it. The broker checks a grant in the operator config, finds the callee's deployment
  running exactly the pinned package, writes a hash-chained audit row naming the caller agent, the
  callee agent and the customer, then signs the callee's token itself and forwards the call.
- The callee acts for the **customer of the caller's current turn**, proven to the broker by the
  host-side signer of that turn, not by the caller agent.
- Each serving agent has an Agent Card (A2A 1.0 shape), derived from its released package and shown
  by `a2a card` and on the console's agent detail with its A2A links. In M19 no card is served on
  the network (A5).

What this is and is not, in words docs may use **once A7 is decided** (§14): "`runtime/adk@1.3.0`
agents call each other through a local broker that checks an operator grant and records each call
in the audit log. A callee on `runtime/adk@1.3.0` refuses calls not signed with its own key; the
broker and anyone who can read your local AgentBreeder state hold that key, so a grant restricts
agents, not you. A compromised caller can still attribute a call to the customer of any of its own
open turns." Grants cover only `runtime/adk@1.3.0` callees: an older agent verifies nothing.
"Granted" and "refused" describe the broker; a compromised agent can still reach other containers'
ports, and only their token checks stop it. Nothing here is enforcement outside the agents'
containers and the broker: no sidecar, no network policy, no Kubernetes support. Docs never call
A2A "enforced" or the audit log "tamper-evident" (a docs test greps for both).

Acceptance (#835, on its own, local Docker):

1. Two agents call each other through the broker on `runtime/adk@1.3.0`, **in sequence**: A@1.0.0
   calls B@1.0.0; then B@1.1.0 (which pins A@1.0.0) is released over B@1.0.0 and calls A@1.0.0.
   Pinned references are acyclic (§8.2), and one agent entry has one production deployment, so
   after the second step A@1.0.0's calls to B get `A2A_CALLEE_UNAVAILABLE` (§8.5) until A is
   rebuilt. Each
   call has an allow and a completion row in the host audit log naming caller, callee and
   customer.
2. A call without a grant is refused by the broker with a deny row; a direct call from A's
   container to B's `/a2a` or `/invoke` without a broker-signed token gets 401.
3. The callee's in-process tools see the customer of the caller's turn; a body or message field
   cannot change it.
4. A call naming a turn that is not open for the caller (unknown, expired, closed, or another
   deployment's) is refused (`A2A_TURN_UNKNOWN`) with a deny row.
5. No broker token, invoke key, master or signed token appears in images, labels, env, logs,
   traces, audit detail, store rows, `center.sqlite3`, `--json` output or argv (the #780 AC3
   canaries, extended).
6. Northwind still passes 61/61 on `runtime/adk@1.3.0`.

## 3. Scope and non-goals

In scope:

- `agent.yaml`: `agents:` (callees, by `agent/` ref) and `a2a:` (opt in to being called, with the
  card's skills). Lock v2 entries for `agent/` refs (M13 §9 contract).
- The deploy manifest's `a2a_access` and the operator config's per-agent `a2a` grant.
- `runtime/adk@1.3.0`: `POST /a2a` (`SendMessage`, text only, blocking), an
  in-process tool per callee, and acceptance of the `act` claim for broker-signed calls.
- The broker: one host process per state directory, turn registry, grants, audit rows,
  signing, forwarding.
- CLI: signers register turns; `a2a list|card`; `status` shows the broker.
- Console (lane B): Agent Card and A2A links on the agent detail.

Non-goals (not built, not claimed):

- Calling or being called by agents outside this state directory: other machines, other
  AgentBreeder installs, non-AgentBreeder A2A agents. External A2A interoperability is not
  claimed; only the listed `SendMessage` subset is tested against the reference SDK (§6.6).
- Remote `agent/` packages (M9b §6.4, deferred by M13 D5 to M19): see A6. M19 does not decide it.
- Kubernetes (`kind`) A2A: refused (`A2A_KUBERNETES_UNSUPPORTED`, A8). `mcp_http`: refused
  (`A2A_ENFORCEMENT_UNSUPPORTED`).
- Streaming (`SendStreamingMessage`), tasks (`GetTask`, `ListTasks`, `CancelTask`,
  `SubscribeToTask`), push notifications, multi-turn contexts (`contextId`), non-text parts
  (files, data), the extended card.
- Policy over A2A calls (Cedar/OPA conditions on caller, callee, customer): #742 owns policy. M19
  grants are a static allow-list, like MCP grants.
- Per-turn binding stronger than "an open turn of this caller" (§7.4 residual).
- An end user proven by an IdP (#780 D3).

## 4. Terms

- **Caller** (A) and **callee** (B): deployments on `runtime/adk@1.3.0` in the same environment
  and state directory.
- **Turn**: one verified `/invoke` or `/a2a` request being processed by an agent, identified by
  the `jti` of the token that started it (#780 §6.4 already records it).
- **Open turn**: a turn the broker has registered for a deployment and that is neither closed nor
  past its deadline.
- **Broker token**: a per-container-generation secret that authenticates an agent to the broker,
  minted like the relay token (`mcp.mint_token`, 256-bit hex, `_FILE`, the broker keeps only its
  sha256).
- **Signer**: host-side code that signs an invocation token from a deployment's host-only master:
  the CLI (`invoke`, `eval`, `release`, `promote`, `token`, the console through `invoke`) and the
  broker.

## 5. Protocol (checked against A2A 1.0.0, 2026-11-13)

The plan and the console spec (§4.6) name `message/send` and `/.well-known/agent.json`. Those are
A2A 0.2/0.3 names. The latest released specification (1.0.0,
`https://a2a-protocol.org/latest/specification/`) names the operation `SendMessage`, the card
path `/.well-known/agent-card.json` (§8.2), requires an `A2A-Version` header from clients (§3.6.1;
an empty value means 0.3) and lists interfaces in `supportedInterfaces` (§4.4.6). M19 implements
1.0 only (A4) and corrects the plan's wording in its docs.

### 5.1 Agent Card

Derived from the released package (M13 §5.2: `manifest.yaml`'s description and the byte copy of
`agent.yaml`, whose `a2a.skills` give the skills), so the card a caller sees is the released one and
`package.json` needs no new field. **Not served on the network in M19** (A5): the caller's tool
description is fixed at build time (§6.3), and `a2a card` and the console read the package, so a
served card would have no consumer (r1 and r2 reviews). The runtime serves none, and neither does
the broker.

```json
{
  "name": "billing",
  "description": "<agent.yaml description>",
  "version": "1.4.0",
  "supportedInterfaces": [{"url": "", "protocolBinding": "JSONRPC",
                           "protocolVersion": "1.0"}],
  "capabilities": {"streaming": false, "pushNotifications": false, "extendedAgentCard": false},
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "skills": [{"id": "refunds", "name": "Refunds", "description": "...", "tags": ["billing"]}]
}
```

- Exactly these fields; no `securitySchemes` (the only caller is the broker, which is not an A2A
  client of a published scheme), no `provider`, `iconUrl` or `signatures`.
- `version` is the package version; `supportedInterfaces[0].url` is empty: the card is not served,
  and the broker route is per caller alias (`/a2a/<alias>`), so a callee has no single URL.
- Strings are bounded (name 64, description 1 KiB, ≤ 16 skills, each field ≤ 256 B) and
  validated at `build`; the card is at most 16 KiB.

### 5.2 `SendMessage`

`POST /a2a` with `Content-Type: application/json`, `A2A-Version: 1.0`, a JSON-RPC 2.0 request:

- `method` exactly `SendMessage`; `params.message` with `role: "ROLE_USER"` (the 1.0 enum value,
  to be confirmed against the reference SDK in slice 1), `messageId` (≤ 64 chars), and `parts`:
  1–8 parts, each exactly `{"text": "..."}`; total text ≤ 16 KiB. `contextId`, `taskId`,
  `referenceTaskIds`, `extensions`, `metadata` and non-text parts are refused
  (`-32602 Invalid params`). `params.configuration` is accepted only as absent or
  `{"blocking": true}` with no other keys.
- The result is a **Message** (allowed by §3.1.1: "MAY return a direct Message response"), role
  agent, one text part with the agent's reply (≤ 64 KiB), a fresh `messageId`. No Task is created.
- `role` and every enum and field name are checked against the 1.0 reference SDK's types in slice
  1; this section is corrected if they differ.
- Errors: JSON-RPC errors with fixed messages: `-32600` invalid request, `-32601` method not
  found (any other method), `-32602` invalid params, and the 1.0 `VersionNotSupportedError` for a
  missing or other `A2A-Version`. Authentication failures are HTTP 401 before any JSON-RPC
  processing (#780 §6.3 order).
- Each `SendMessage` runs in a **fresh ADK session** of the callee for the propagated customer;
  multi-turn contexts are a non-goal.

## 6. Runtime: `runtime/adk@1.3.0`

Built on 1.2.0 (#780 §7), which stays byte-for-byte. Manifest: `invocation: token-v1`,
`capabilities: [mcp, a2a]`; environment adds `AGENTBREEDER_A2A_BROKER_URL` and secrets add
`AGENTBREEDER_A2A_BROKER_TOKEN` (as `_FILE`), both only when the agent has callees.

### 6.1 Verifier changes (callee side)

- Accepts the `act` claim **only** together with `cal: a2a`, as `{"sub": "<caller deployment id>"}`
  optionally nesting the previous actor (`{"sub": …, "act": {…}}`, RFC 8693 §4.1), depth ≤ 3. Any
  other `act` shape is `TOKEN_INVALID`. `cal` stays informational (#780 §6.2): `act` is recorded,
  never used for a decision inside the callee.
- Everything else is #780 §6.2–6.3 unchanged: same key (`k_invoke`), same order, `jti` single use,
  `bh` bound, customer only from `sub`.
- The `act` chain and `cal` go into the `detail` of the turn's first `audit_events` row and the
  span attribute `agentbreeder.actor_chain` (deployment ids only).

### 6.2 Serving

- `POST /a2a`: §5.2 after the #780 checks. Refused unless the agent's `agent.yaml` opted in
  (`a2a: {serve: true}`): 404 for a non-serving agent, so a granted caller cannot reach an agent
  that did not opt in to serve.
- `POST /invoke` unchanged.
- The session lock is `(customer, session)` (#780 §6.4); each A2A call gets a fresh random session
  id (tested), so two callers cannot collide.

### 6.3 Calling (caller side)

- One in-process ADK `FunctionTool` per callee, named `ask_<alias>` (alias from `agents:`,
  `^[a-z][a-z0-9_]{0,31}$`), taking one string argument `message`. Its description is the callee
  card's `description` plus its skill names, **from the locked package at build time**
  (`agent.config.json`), never fetched at run time, so a callee cannot rewrite the caller's tool
  list (prompt injection through a live card).
- The tool posts §5.2 to `AGENTBREEDER_A2A_BROKER_URL` + `/a2a/<alias>` with
  `Authorization: Bearer <broker token>` and `AgentBreeder-Turn: <jti of the current turn>`. ADK's
  `ToolContext` has no slot for it; the runtime already keeps per-turn state in `self.turns`, keyed
  by `tool_context.invocation_id` (`agent.py` `tool_runtime`). The verified `jti` is passed from the
  server through `chat()` into that entry (the same plumbing #780 1.2.0 adds for the customer), and
  the tool reads it from there, never from a shared or module-level value, so concurrent turns of
  different customers never mix; a two-customer concurrency test pins it. The `jti` is not a
  credential (§7.4).
- No customer is sent: the broker takes it from the registered turn.
- The reply text is returned to the model as the tool result, marked as content from another
  agent (`{"agent": "<alias>", "reply": "..."}`). Broker refusals become a tool error with the
  fixed code only.
- Timeouts: the tool's deadline is the turn's remaining time less 10 s, at most 170 s.
- Redaction (`runtime/redaction.py`) remembers the broker token.
- ADK's `RemoteA2aAgent` is not used: it fetches the card at run time, adds `a2a-sdk` and an
  `httpx` client to the runtime and has no place for the per-turn header. A conformance test uses
  the reference SDK on the **test** side only (§6.6).

### 6.4 Not changed

The MCP client, relay path, memory schema (no DDL), `/health` (`{"status": "ok"}`), and the
removed chat page (if #780 D2 is decided that way).

### 6.5 Config and start

`config.py` reads the broker URL and token file only when callees are configured; a missing or
short token fails the start. A callee-only agent has neither.

### 6.6 Conformance

Slice 1 pins `a2a-sdk` (test extra only) and checks the protocol vectors against it: every request
the tool builds and every response the runtime returns parses with the SDK's 1.0 types, and every
§5.2 request the SDK's types produce for a text message is accepted. Running the SDK's client
against `/a2a` would need a per-request signing hook (`bh` binds each body), so it is not claimed.
Docs may say "A2A 1.0 `SendMessage` message shape (text, blocking)" only after these tests pass;
nothing broader, and no claim of interoperability with other A2A implementations.

## 7. The broker

### 7.1 Placement and lifecycle (A1)

One host process per state directory: `python -m agentbreeder.a2a.broker --state-dir DIR`,
standard library plus AgentBreeder modules, like `egress/host.py`.

- Started by `deploy` (inside the lifecycle lock, after the identity gate) when the deployment has
  `a2a_access` or serves A2A and no healthy broker of the current AgentBreeder version is running
  (a stale one is replaced, which drops every open turn of every deployment, so in-flight calls
  fail closed; `deploy` says so); spawned with `start_new_session=True`, as the egress host is
  (`egress/boundary.py`), so a signal to a console child's process group does not kill it.
  Stopped by `remove` when no A2A deployment remains. `reconcile` restarts a dead broker and
  reports it. `status` shows `a2a broker: running | stopped | unhealthy | port taken`.
- **Port.** One loopback port per state directory, allocated once and kept in the pin file across
  restarts, because callers' `AGENTBREEDER_A2A_BROKER_URL` is fixed at deploy. If the port is taken
  when the broker starts, it does not move: `reconcile` and `status` report `port taken` and A2A
  calls fail closed until the operator frees it (tested).
- **Transport.** Only Docker Desktop's path is designed and claimed: loopback TCP, reached by
  containers as `host.docker.internal:<port>` (`egress/boundary.py` `listen_mode` returns `tcp`
  there). Any local process and any container can reach the port, so every request is
  authenticated (§7.2) and refusals are cheap (#780 §6.3's 10 s header timeout,
  `Connection: close`, 2 KiB `Authorization` limit). Traffic is plaintext HTTP on loopback, so,
  as #780 T2, protection is "same OS user only". A Linux Unix-socket mode (socket directory 0755,
  a bind mount in `deployment.py`, a socket-capable client in the runtime) is left to a later slice
  and refused until then (`A2A_PLATFORM_UNSUPPORTED`); CLAUDE.md records Linux as verified only for
  install, `--version` and `doctor`.
- **Capacity.** At most 64 connections; at most 4 concurrent calls per caller deployment
  (`A2A_BUSY`); 8 connection slots are reserved for `/turns` and `/healthz`, so a caller holding
  calls open cannot block turn registration.
- It reaches callees as `invoke.py` does: `http://127.0.0.1:<published port>` of a container it
  verified through Docker (labels, deployment id, running), no proxies or redirects, and it
  re-checks the container ID right before it connects.
- Threaded (calls last up to 170 s); audit writes and store reads go through one lock and one
  SQLite handle, as `egress/host.py` serializes decisions, and rely on `audit.py`'s
  `BEGIN IMMEDIATE` to serialize with CLI writers in other processes (a cross-process test).
- State on disk: the pin file (`a2a-broker/pin.json`, 0600: pid, version, port, start time) and the
  grant files of §7.2; nothing else. The turn registry is in memory: a broker restart drops every open turn, so
  in-flight A2A calls fail closed (`A2A_TURN_UNKNOWN`).
- **Blast radius.** The broker reads every A2A deployment's host-only master on demand. That is no
  more than the CLI can read, but it is a long-lived process holding that reach; a compromise of it
  is a compromise of every A2A deployment's key (A-T11).

### 7.2 Authenticating the caller agent

- `deploy` of a deployment with `a2a_access` mints a broker token per container generation
  (revoking the previous one first, as `_grant_mcp` does), writes it with
  `secret_files.write_generated(..., "a2a-broker-token", "AGENTBREEDER_A2A_BROKER_TOKEN", token)`,
  and writes a grant file `a2a-broker/grants/<sha256(token)>.json` (0444 in a 0700 directory;
  the broker runs as the operator, so no 0755 is needed): deployment id, agent name, environment.
  No callee list: grants are re-read from the operator config on every call (§8).
- The grant file also records the container generation it was minted for; a redeploy revokes the
  old file before minting (§7.5 step 3 needs no store marker).
- The presented bearer value must match `^[0-9a-f]{64}$` (as `mcp.py` `TOKEN` for the relay) before
  it is hashed; the file name is only ever `sha256(token).json`, never derived from a header
  (traversal and garbage-token tests).
- `remove`, a failed deploy's cleanup and `reconcile` delete the grant file (`_revoke_mcp`
  pattern). A missing grant file is `A2A_CALLER_UNKNOWN` (401).

### 7.3 Endpoints

| Endpoint | Caller | Purpose |
|---|---|---|
| `POST /turns` | host signers | register a turn (§7.4) |
| `DELETE /turns/<jti>` | host signers | close a turn |
| `POST /a2a/<alias>` | agent (broker token + turn) | §7.5 |
| `GET /healthz` | `status`, `reconcile` | nonce-answered liveness, as the egress host |

### 7.4 Proving the caller's turn and customer (the main question)

The broker must learn *which customer* A is acting for, without A holding anything that proves
it. A holds its `k_invoke` and sees every token sent to it, so any proof that travels through A,
or that A could compute, is A's to reuse.

**Design (A2, recommended): the signer registers the turn with the broker before it calls the
agent.** For a deployment with `a2a_access`:

1. The signer (CLI or broker) mints the invoke token as #780 §6.2 (`jti` J, `sub` C).
2. Before sending it, it posts a **turn registration** to the broker: a compact JWS under
   `k_turn = HKDF-SHA256(master, info = "agentbreeder:a2a-turn:v1:<deployment id>")`, a key derived
   from the same host-only master (#780 §6.1) and **never mounted**, so the agent cannot derive or
   forge it. Claims: `iss`, `aud = agentbreeder:a2a-turn:<deployment id>`, `sub` (customer, or
   absent for `guest`), `jti` = J, `iat`, `exp` = the invoke token's `exp`, `dl` = turn deadline
   (`exp` + 180 s), `op: "open"`, and for broker-made turns `act` (the chain). Same strict parsing
   rules as #780 §6.2, and a claim set disjoint from invoke tokens (`op` and `dl` are refused by
   the invoke verifier; `bh` and `cal` are refused here). The broker verifies it with `k_turn`,
   which it derives from the master itself. It refuses a registration whose `iat` is before the
   broker's own start (less 60 s skew), so a captured registration cannot be replayed after a
   restart empties the seen-set, and one with `dl - iat > 480`. The deployment id in the HKDF
   `info` is 32 lowercase hex (`uuid4().hex`, `deployment.py`), so labels cannot collide; a vector
   pins it.
3. The broker records the open turn `(deployment, J) → (customer, deadline, chain, depth, root)`;
   a second registration of J is refused, including after J is closed: the seen-set keeps J until
   its `dl` (tested), and a deployment has at most 256 open turns
   (`A2A_BUSY`).
4. The agent's tool names J in `AgentBreeder-Turn` (§6.3). The broker accepts it only if J is an
   open turn **of the deployment its broker token belongs to**.
5. The signer closes the turn (`DELETE /turns/J`, authenticated by a second `k_turn` JWS with
   `op: "close"`, whose `jti` must equal the path's J) when the agent's response arrives; the
   deadline closes it otherwise. A closed turn's calls in flight finish; new ones are refused.
   Broker-made turns get `dl = min(parent dl - 10 s, now + 170 s)`.

Key labels (all HKDF-SHA256 over the #780 §6.1 master, `info` = label + deployment id):

| Label | Key | Held by |
|---|---|---|
| `agentbreeder:invoke:v1:` | `k_invoke` | host signers, the agent (mounted) |
| `agentbreeder:attr:v1:` | `k_attr` (#780 §8.2, not built) | host decision service only |
| `agentbreeder:a2a-turn:v1:` | `k_turn` | host signers and the broker only |

If #780 D1 chooses Ed25519, deploy still mints a 32-byte host-only seed per container generation,
and `k_turn` derives from that seed with the same label.

Why this shape: the proof (`k_turn`, the registration) goes host to host and never passes through
A; what A holds (J, its broker token) proves nothing alone. The registration happens on the host
that already holds the master, so it adds no new secret.

**Residual, stated in the docs:**

- A's process knows the `jti` of each of its own open turns. Compromised in-process code (a tool
  package, a dependency) can therefore attribute a call to **the customer of any of A's own
  currently open turns**, for example another customer whose turn is running concurrently. It
  cannot name a customer for whom no host signer opened a turn on A, cannot use another
  deployment's turns, and cannot call after the deadline.
- A broker token plus a J exfiltrated from A works from **any local process or container**, since
  on Docker Desktop the broker listens on loopback TCP reachable as `host.docker.internal`; only
  for A's grants and only until J closes.
- A compromised callee B can likewise use any of **B's** open turns, including turns a host signer
  opened directly on B with an empty chain. The depth, cycle and per-turn limits therefore bound
  honest chains and each root turn, not a compromised agent; the per-caller concurrency cap
  (§7.1) bounds its parallelism.
- Turns registered by `token` cannot be closed by the signer and stay open until `exp` + 180 s (up
  to 480 s).
- J is recorded in the runtime's `audit_events` detail and span (#780 §6.4), so anyone who reads
  traces learns it; it is useless without the matching broker token.
- **Confused deputy.** A prompt-injected caller (or customer text) can send B any message, and B
  acts for that turn's customer with B's own tools. A grant covers the whole callee, not its
  skills.

Closing the first point needs a per-turn secret issued on a path A does not control (a sidecar on
A's ingress, #780 §8.2); not in M19.

Alternatives considered:

- **A forwards an attribution token it received** (signed under a key A lacks): simpler, no
  registration, but A then holds a bearer proof it can replay for that turn's lifetime from
  anywhere that reaches the broker. Rejected by #780 §9's rule.
- **A per-turn nonce issued by a sidecar on A's ingress** (#780 §8.2): closes the residual but
  cannot run today (`MCP_RELAY_UNSUPPORTED`, `MODEL_ACCESS_UNSUPPORTED`). Later, under #742.
- **No customer propagation** (callee always `guest`): no residual, but the callee cannot act for
  anyone; A3 keeps this as a per-grant option.

### 7.5 A call (`POST /a2a/<alias>`)

In order; any failure answers the agent with a fixed code, writes a **deny** row (§10) unless the
caller could not be identified (401s are counted, not audited row by row, as #780 §6.3 refusals),
and forwards nothing. Deny rows are bounded: the first deny per (caller, code) in a minute is
written, later ones in that minute are counted into one `a2a_call/deny_summary` row, so a caller
cannot flood the chain or starve allow rows (tested).

1. Header checks (as #780 §6.3 1–2); `Authorization` → grant file → caller deployment A, else
   401 `A2A_CALLER_UNKNOWN`.
2. `AgentBreeder-Turn` → open turn of A, else `A2A_TURN_UNKNOWN`.
3. A is active, its state is not `disabled`, it has a bound `principal_key` and that principal is
   not blocked by the kill switch (`store.blocker(principal_key, environment)`, as deploy and
   `verify` check it), else `A2A_CALLER_DISABLED`; an unbound deployment fails closed the same
   way. The callee gets the same check in step 6. Concurrency cap (§7.1), else `A2A_BUSY`.
4. `alias` is in A's deploy manifest `a2a_access`, giving the callee ref and tree hash, else
   `A2A_CALLEE_UNKNOWN`.
5. The operator config (re-read and pin-checked per call, as `egress/host.py` does) grants A's
   agent the callee's agent name, which is the package name of the ref (`agent/<name>@…`) and must
   be an agent key of this environment (§8.4), else `A2A_NOT_GRANTED`.
6. Callee resolution (§8.5): exactly one active, not-blocked, non-candidate deployment in A's
   environment whose manifest `identity` equals that agent entry's `identity`, whose running
   container's image ID (from `docker inspect` of the container verified as `invoke.py` verifies it,
   not from the manifest's image reference, which can be a moved tag) equals the lock's
   `pin.image`, that has an M13 package link (any version, M13 §7.3) to a package with that image,
   whose manifest serves A2A (`a2a_serve: true`) and is `invocation: token-v1`; else
   `A2A_CALLEE_UNAVAILABLE` or `A2A_CALLEE_AMBIGUOUS`.
7. Depth: the new chain has ≤ 3 actors and the callee is not already in it (no cycles), else
   `A2A_DEPTH` or `A2A_CYCLE`. Per turn at most 16 calls, else `A2A_LIMIT`.
8. Body: §5.2 shape, size ≤ 20 KiB, else JSON-RPC `-32602`.
9. Write the **allow** row (§10) with a fresh `attempt_id`. If the audit write fails, refuse
   (`A2A_AUDIT_FAILED`).
10. Mint the callee's token (#780 §6.2 under B's `k_invoke`, derived from B's host-only master):
    `cal: a2a`, `sub` = the turn's customer (or none, if A3's per-grant `customer: none` is chosen
    and set), `act` = `{"sub": A}` nested over A's own chain, a new
    `jti` J', `bh` over the exact bytes forwarded, lifetime 60 s. If B has callees, register J' as
    B's turn first (§7.4, chain and depth carried), so B → C works and is attributed to the same
    customer.
11. Forward to B's `POST /a2a` with the deadline of step 2's turn less 10 s. Return B's JSON-RPC
    result to A unchanged in shape but re-serialized from the validated fields only (one text part,
    ≤ 64 KiB, C0/C1 control characters other than newline and tab removed, so no ANSI escapes
    reach logs or terminals). B's HTTP or JSON-RPC errors map to `A2A_CALLEE_ERROR` with the
    callee's code.
12. Close J' and write a **completion** row (`ok`, `callee_error`, `timeout`) with the same
    `attempt_id` and the duration. If that write fails, the reply is dropped and A gets
    `A2A_AUDIT_FAILED`. At start, the broker writes an `a2a_call/abandoned` row for each allow
    row of its previous run that has no completion (a crash between steps 9 and 12; tested).

The broker never logs message text, replies, tokens or headers; its stdout carries one line per
call with codes, deployment ids and duration.

## 8. Grants and references

### 8.1 `agent.yaml` (authoring schema)

```yaml
agents:                       # callees (caller side)
  - ref: agent/billing@1.4.0  # an M13 package, local only (A6)
    as: billing               # tool alias: ask_billing; default the package name
a2a:                          # callee side: opt in to being called
  serve: true
  skills:
    - {id: refunds, name: Refunds, description: "Issue and track refunds", tags: [billing]}
```

- `agents:` ≤ 8 entries, unique aliases, refs of kind `agent` only. A ref of another kind is the
  existing wrong-kind error (`agentfile.py`).
- `a2a.serve` defaults to false; `skills` ≤ 16 and only with `serve: true`.
- JSON Schema and `docs/agent-yaml.md` updated.

### 8.2 Lock

Each `agents:` ref is a lock v2 entry in the M13 §9 shape, `{"sha256": <tree>, "source":
"registry", "pin": {"image": "sha256:<id>"}}`. That is a change to M9b's lock schema (M9b §7
refuses unknown `pin` keys); M13 §9 assigns it to M19 unless M9b slice 1a already allows it.
`build` checks `pin.image` against the package's `image.id` and refuses a package whose
`agent.runtime` is older than `runtime/adk@1.3.0` or whose `agent.yaml` copy does not set
`a2a.serve: true` (`A2A_CALLEE_RUNTIME`, `A2A_CALLEE_NOT_SERVING`). An `agent/` entry forces lock
v2. `build` and `materialise` copy no `agent/` content into the build context; only the card's
description and skill names go into `agent.config.json` for the tool.

**The pinned graph is acyclic.** A's package holds A's lock, which pins B's tree hash and image;
B's package does the same for its callees. Two versions cannot pin each other, since each would
have to exist before the other. Mutual calling is done across versions (A@1 → B@1, then B@2 →
A@1). `build` cannot meet a cycle among existing packages; the broker's cycle check (§7.5 step 7)
is defence in depth.

### 8.3 Deploy manifest

`build` writes `a2a_access: [{alias, ref, sha256, image}]` and `a2a_serve: bool` into the v2 deploy
manifest (`a2a_serve: bool | None`, never written as `false`); `Manifest` validates and preserves them through `model_validate` round trips (release
and promote rebuild manifests). Both are optional, and the `exclude` tuple of `Manifest.digest()`
(`manifest.py`) gains both names, so they are left out when `None`, as `model_access` and
`mcp_access` are, so existing deployments keep their
digest (no `NAME_CONFLICT` on redeploy; a digest-stability test). A manifest that sets them is
refused by older CLIs (`extra="forbid"`), as any new field is; the CHANGELOG says so. JSON Schema
updated.

### 8.4 Operator config

`AgentIdentities` gains `a2a: list[str]` (≤ 16 agent names of the same environment, unique),
beside `mcp`. **Identity-to-grant resolution** is `_mcp_servers`'s (`deployment.py`): the caller
deployment's `manifest.identity` is matched against each environment agent's `identity` or
`candidate_identity`, and that agent entry's `a2a` list applies. The **callee's** agent name is the
package name of the ref (`agent/billing@…` → `billing`), which must be an agent key of the
environment; the broker then requires the callee deployment's manifest `identity` to equal that
entry's `identity` (§7.5 step 6), so a deployment cannot answer for an agent it is not. Deploy-time
checks and the broker use the same mapping, which needs no callee deployment. A `-candidate`
deployment name is never used for matching. If A3's per-grant option is chosen, `a2a` becomes
`list[str | {agent, customer}]`. The grant
names an **agent**, not a version: the version is pinned by the caller's `agent.yaml` and checked
by the broker (§7.5 step 6). A3's per-grant customer option, if chosen, is
`a2a: [{agent: billing, customer: propagate | none}]`.

Release candidates (A11): a candidate of A (`release` deploys `<name>-candidate` with
`candidate_identity`, `release.py`) is granted as A, so its evals call the production callee for
real, with the eval case's customer, as candidate MCP calls through the relay already do. A
candidate is never a callee (§7.5 step 6). Eval signers register and close one turn per case;
concurrent cases are independent turns.

Deploy-time check (beside `_mcp_servers`): every `a2a_access` alias's callee agent must be granted
(`A2A_NOT_GRANTED`, exit 2), the environment must not use `mcp_http`
(`A2A_ENFORCEMENT_UNSUPPORTED`) and the target must be local Docker (`A2A_KUBERNETES_UNSUPPORTED`).
The callee does not have to be deployed yet; the broker checks that per call.

### 8.5 Callee resolution and the callee's lifecycle

A pin means "the image A was built and evaluated against". The broker matches on that image
(§7.5 step 6), not on the version label, so:

| B event | A's calls |
|---|---|
| B re-released with the same image (M13 `link_package` moves to the new version) | keep working |
| B released with a new image, B rolled back to another image, or B deployed from a plain `agent.yaml` without a package link | `A2A_CALLEE_UNAVAILABLE` until A is rebuilt and released against the new package; `a2a list` shows `callee stale` |
| B disabled (kill switch) | `A2A_CALLEE_UNAVAILABLE` |
| B removed during a call | the call fails (`A2A_CALLEE_ERROR`); the completion row records it |

Each row is a test. This is intended: A's evals proved A against B's image, not B's name.

### 8.6 Interplay with #780 decisions (all open)

- **D1** (HMAC or Ed25519): independent. The broker signs from the host-only master either way;
  with Ed25519 the callee would hold only a public key.
- **D2** (chat page): independent.
- **D3** (external customer identity): a later IdP-proven customer would be what the signer
  registers; the broker would not change.
- **D4** (`require_authenticated`): A2A requires `invocation: token-v1` on both sides regardless.
- **D5** (relay learns the customer): independent; the callee's relay calls still carry no
  customer.
- **D7** (§8.2 sidecar under #742): the sidecar's per-turn nonce is the path to closing §7.4's
  residual.
- **D8** (no host audit per signed CLI call): unchanged for `/invoke`; the broker is a separate,
  long-lived writer like the egress host and records each A2A call. Turn registrations are not
  audited (they are as frequent as invokes).
- **D9** (claim rule): A7 extends it.

## 9. CLI, engine and packages

### 9.1 Signers

`invocation.py` (#780 §8.4) gains `register_turn` and `close_turn`. Every signer path (#780 §6.5:
`invoke`, `eval`/`release` candidate, `promote`, `token`, console via `invoke`) registers the turn
when the target deployment's record has `a2a_access`, and closes it after the response. If the
broker cannot be reached, the call stops before anything is sent (exit 2,
`A2A_BROKER_UNAVAILABLE`, "run `agentbreeder reconcile`"), because a turn whose A2A calls all fail
is worse than a clear error. `token` registers the turn at mint time, deadline `exp` + 180 s, and
cannot close it (the deadline does). `invoke` keeps its read-only state open (M4); registration
goes to the broker, not the store.

### 9.2 Engine (`deployment.py`)

- Deploy: §8.4 checks; broker token and grant file (§7.2); `AGENTBREEDER_A2A_BROKER_URL`;
  broker start (§7.1). Audit event
  `a2a_grant / minted` (deployment id only).
- Remove and failed-deploy cleanup: delete the grant file and the token copy; stop the broker if
  no A2A deployment remains.
- Store: no new column and no schema version. The store keeps each deployment's manifest as JSON
  (`store.py`), which carries `a2a_access` and `a2a_serve`, as it will carry #780's `invocation`.
  M13's schema v4 is unaffected.

### 9.3 Packages (M13)

No package format change: the card is derived from the package's `manifest.yaml` and `agent.yaml`
copy (§5.1), so `package_version` stays 1 and lane C's `package.json` schema is untouched.

### 9.4 New commands

- `agentbreeder a2a list [--json] [--state-dir|--stack]`: each A2A deployment, its callees (alias,
  ref, granted yes/no, callee deployed yes/no), whether it serves, and the broker state. Read-only.
- `agentbreeder a2a card NAME|agent/<name>@X.Y.Z [--json]`: the card from the package. Read-only,
  no network.
- `audit list` gains `--action ACTION` and `--mode MODE` filters (today it takes only `--limit`,
  `--attempt`, `--state-dir` and `--json`, `commands/audit.py`), so `audit list --action a2a_call`
  and `--mode a2a_broker` work; tested. `--attempt` already lists one call's rows.

## 10. Audit

Host hash-chained log (`audit.py`), written by the broker before it forwards:

| Field | Value |
|---|---|
| action / decision | `a2a_call` / `allow` or `deny`; then `a2a_call` / `completed`, with the result (`ok`, `callee_error`, `timeout`) as an `A2A_RESULT` reason (the audit table has a `decision` column and no outcome column) |
| actor | `agent:<caller agent name>`, `actor_verified` false (the broker authenticates a deployment's token, not an identity-provider principal) |
| attempt id | one per call, shared by the allow and completion rows |
| enforcement mode | `a2a_broker` (a new value of the required `AuditEvent.enforcement_mode`; `audit list --mode`, §9.4) |
| deployment id, image | the caller's deployment id; the callee's image ID |
| reasons | `A2A_CALLER` (deployment id, agent), `A2A_CALLEE` (deployment id or none, agent, package ref), `A2A_CUSTOMER` (customer id or `guest`), `A2A_TURN` (J), `A2A_CHAIN` (deployment ids), the refusal code for a deny |

- Never message text, replies, tokens, headers or card text.
- The customer id in the host chain is new: until now only the runtime's `audit_events` held
  customer ids. Customer ids are AgentBreeder's opaque identifiers (`^[A-Za-z0-9_-]{1,64}$`); M16's
  `memory forget` cannot remove them from the chain (A10).
- The callee's runtime also writes its own `audit_events` row with `cal: a2a` and the `act` chain
  (§6.1), so the call can be followed from the broker row (J') to the callee's turn.
- The 50-reason cap (`deployment.py`) is far from reached; a test pins it.

## 11. Threat model

Trust boundary as #780 §5: the operator's OS user on a single-user machine. The broker runs as
that user.

| # | Threat | After M19 |
|---|---|---|
| A-T1 | A calls an agent it is not granted | refused by the broker (deny row); a `runtime/adk@1.3.0` callee refuses calls not signed with its own key (401). Older callees verify nothing and are outside any grant |
| A-T2 | A names an arbitrary customer for B | an arbitrary customer: impossible (it comes from a host-registered turn); the customer of any of A's open turns: possible (A-T3) |
| A-T3 | Compromised code in A (or B, for nested calls) uses another of its own open turns | **open** (§7.4 residual); docs state it |
| A-T4 | A container on the agents network, or a local process, calls the broker | needs a broker token (401); on Docker Desktop's TCP listen anyone local can try; tokens are 256-bit, looked up by hash only |
| A-T5 | A captured broker token + J used elsewhere | only for A's grants, only until J's deadline (≤ token TTL + 180 s) |
| A-T6 | Prompt injection between agents: the callee's card or reply into A, or A's (possibly injected) message into B | the card text is pinned at build (no live card); replies are tool output marked as another agent's, control characters stripped; injection itself is not prevented, and B acts on any message from a granted caller with the turn's customer (confused deputy, §7.4) |
| A-T7 | Call loops and cost amplification | honest chains: depth ≤ 3, no cycles, 16 calls per root turn, deadlines shrink per hop; a compromised agent: bounded only per open turn and by the 4-call concurrency cap |
| A-T8 | A flood of turn registrations, calls or deny rows | registrations need `k_turn` (host-only); calls need a broker token; 10 s header timeout, 64 connections with 8 reserved for `/turns` and `/healthz`, 4 concurrent calls per caller, deny rows summarised per minute |
| A-T9 | Keys leak (broker token, masters, tokens) | #780 AC3 canaries extended to the broker token, registration tokens and broker logs |
| A-T10 | A stale callee (old image) answers | the broker requires the running container's image ID to equal the pin and a package link to a package with that image (§7.5 step 6) |
| A-T11 | The broker process is compromised, or a local process binds its port while it is down | not defended. A compromised broker holds every A2A deployment's key. A squatter cannot sign for callees, but it receives callers' broker tokens, turn ids and message text (which can carry customer data) and can return forged replies. `status` and `reconcile` report a dead broker or a taken port; the same-OS-user boundary is the protection |
| A-T12 | Data from B's customer records reaches A's model | by design for the same customer; docs say the callee's tools act for the propagated customer |
| A-T13 | A Docker-socket user, root, or a reader of the state directory | can sign anything, as in #780 T9 |
