# Changelog fragments and per-command docs (#893)

Status: owner decision recorded on #893 (2026-11-13): a small script (no towncrier), split
`docs/commands.md` into one file per command with a generated index, and a CI check. Part of #812.

## Problem

Every PR adds lines at the same places in `CHANGELOG.md` (`[Unreleased]`) and in
`docs/commands.md`, which is one long paragraph. With several lanes working in parallel, each
merge to `main` makes every other open PR CONFLICTING, and each conflict costs a merge, a test
rerun on 3.11/3.12/3.13, a delta review and a gate pass.

## Goal

Two PRs that each add a changelog entry and edit a command's doc both merge without either
becoming CONFLICTING.

## Design

### Changelog fragments

- A PR adds `changelog.d/<issue>.<type>.md`, or `changelog.d/<issue>.<slug>.<type>.md` when one
  issue needs more than one entry of a type. `<type>` is `added`, `changed`, `fixed` or
  `internal` (the headings `[Unreleased]` uses today); `<slug>` is `[a-z0-9-]+`.
- A fragment is the entry exactly as it will appear: a Markdown list item starting with `- `,
  with no headings, and it says "on `main`, not in a published preview" (checked after joining
  wrapped lines, ignoring case).
- `scripts/changelog.py` (standard library only):
  - `lint`: checks every file in `changelog.d/` (names and content). Run by a pytest test, so it
    runs on every push and PR on 3.11–3.13.
  - `check --labels-json JSON --author LOGIN`: for a pull request. It reads the PR's changes as
    `git diff --name-status --no-renames HEAD^1 HEAD` on the test-merge commit GitHub checks
    out (it refuses a HEAD that is not a two-parent merge). It fails when the PR edits
    `CHANGELOG.md` without the `release` label, and when the PR changes a non-trivial path but
    adds or edits no fragment. Trivial paths: `docs/superpowers/**`, `changelog.d/**`,
    `CLAUDE.md`, `AGENTS.md`, `.agents/**`, `.gitignore`. A `release`-labelled PR and a
    `dependabot[bot]` PR are exempt from the fragment rule. It also runs `lint`.
  - `fold [--dry-run]`: at release, inserts every fragment into `CHANGELOG.md`'s `[Unreleased]`
    under its type's `###` heading (created in the order Added, Changed, Internal, Fixed, as today, when
    missing), at the top of that heading, highest issue number first, then by file name, and deletes the
    fragments. The release PR then renames `[Unreleased]` and edits entries by hand as it does
    today, so the shape, including the "on `main`, not in a published preview" marking, is the
    same.
- `.github/workflows/changelog.yml`: `pull_request` (opened, synchronize, reopened, labeled,
  unlabeled), `contents: read`, checkout with `persist-credentials: false` and `fetch-depth: 2`,
  then `check`. Labels and author are passed through `env`, never interpolated into the script.
- Cut-over: the entries already in `[Unreleased]` stay as they are. From this PR on, PRs add
  fragments; `changelog.d/README.md` and `docs/contributing.md` say so. This PR's own entry is a
  fragment, so it does not edit `CHANGELOG.md` either. An open PR that edited `CHANGELOG.md`
  moves its entry to a fragment when it next merges `main`.

### Per-command docs

- `docs/commands/<command>.md`, one per top-level CLI command (34 today). Each starts with
  `` # `agentbreeder <command>` ``, a blank line, then a one-line summary (the command's
  `--help` line). The rest is the existing text from `docs/commands.md`, moved verbatim and
  split into paragraphs; no new claims.
- `docs/commands.md` keeps its path (CLAUDE.md, specs and plans link to it) and holds the
  install/development text and the cross-command notes (`--stack`, `Next:` lines, stopping
  streamed commands), then an index between `<!-- commands-index:start -->` and
  `<!-- commands-index:end -->`, one line per file, sorted, generated by
  `scripts/commands_index.py --write` and checked by `--check`.
- Tests: the index is current; every top-level command in the CLI parser has a file and every
  file names a command; relative links in `docs/commands*` resolve.
- Two PRs that edit different command files never conflict. Two PRs that each add a new command
  conflict on the index only if their lines are adjacent in sort order; the index is regenerated,
  never hand-merged (as the help goldens are).

## Acceptance

- Two PRs, each with a fragment and an edit to a different command file, merge in either order
  without conflicts (checked by a test that runs `git merge` in a temporary repository).
- `fold` output keeps the existing `[Unreleased]` shape; tested on a copy of today's file.
- The CI check and the updated contributor docs are in place.
- No text from `docs/commands.md` is lost (checked when splitting: every sentence of the old file
  is found in the new files).

## Out of scope

- The help goldens (`tests/fixtures/cli_help/*.txt`), README, `website/` (release R, #836).
- `CLAUDE.md`'s docs rule: the coordinator updates it.
- Making the check a required status: owner's branch-protection setting.
